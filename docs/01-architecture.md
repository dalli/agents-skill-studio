## 1. 개요

### 1.1 시스템의 역할

에이전트 스킬([Agent Skills](https://agentskills.io), 원래 Anthropic이 공개한
표준)의 전체 수명주기 — **작성 → 검증 → 테스트 → 패키징 → 설치 → 임포트** — 를
하나의 데스크톱 애플리케이션에서 제공하는 도구다.

### 1.2 이 시스템이 하는 것과 하지 않는 것

| 하는 것 | 하지 않는 것 (v1 비범위) |
|---|---|
| 스펙 규칙에 맞는 스킬을 작성한다 | 호스팅 스킬 레지스트리를 운영한다 |
| 스펙 위반을 위치와 함께 보고한다 | 외부 레지스트리(skills.sh 등)에	push한다 |
| 스킬이 실제로 도움이 되는지 측정한다 | 범용 에이전트 런타임을 새로 만든다 |
| 재현 가능한 아티팩트를 만든다 | 플러그인 매니페스트(`.claude-plugin/` 등)를 생성한다 |
| 클라이언트가 실제로 찾는 경로에 설치한다 | Cursor `.mdc` 규칙을 편집한다 |
| 출처 불명의 스킬을 검증 없이 통과시키지 않는다 | 여러 사용자·클라우드 동기화를 제공한다 |

비범위의 근거는 [04. 개발 계획 §1](./04-development-plan.md#1-개요)에 기록한다.

## 2. 설계 원칙

PRD §8의 제약 `C1`–`C16`을 구현 가능한 원칙으로 재서술한다.
**이 문서의 `A-n` 번호는 아키텍처 결정 식별자**이며, 제약 번호와 구분된다.

### 2.1 단일 진실 공급원 (Single Source of Truth)

**규칙은 Python(`C2`)에만 존재한다.**

| 계층 | 하는 일 | 하지 않는 일 |
|---|---|---|
| `C1` Rust | 프로세스 수명주기, 네이티브 통합, IPC 라우팅 | **스펙 규칙 판단 금지** |
| `C2` Python | 모든 규칙 · 검증 · 판정 | — |
| `C12` TypeScript | 표현 · 상태 · 사용자 입력 | **규칙 재구현 금지** |

`C12`가 `name` 규칙을 다시 구현하면 세 언어의 규칙이 서로 다른 시점에
수정되어 반드시 어긋난다. 프런트엔드는 `C2`에게 검증 결과를 요청하고
표시만 한다. 유일한 예외는 [§7.1](#21-단일-진실-공급원-single-source-of-truth)과
[§10.2](#92-캐시)의 경량 사전 검사로, 각각 근거를 명시한다.

**근거:** 스펙이 자주 바뀐다(클라이언트가 필드를 더한다). 규칙이 한 곳에
없으면 그때마다 세 군데를 고쳐야 하고, 한 곳을 빠뜨리면 사용자는
"검증기를 통과했는데 클라이언트가 안 읽는다"를 겪는다.

### 2.2 실패-닫힘 (Fail-Closed)

보안 통제가 실패하면 **시스템은 열리지 않는다.** 샌드박스를 세울 수 없으면
샌드박스 없이 실행되지 않고 **오류**를 낸다. 검증에 실패하면 설치하지 않는다.

| 잘못된 대안 | 왜 위험한가 |
|---|---|
| 샌드박스 실패 → 격리 없이 실행 | "샌드박스와 없음"이 구별되지 않는다. 사용자는 안전하다고 오해한다 |
| 검증 실패 → 경고만 표시하고 설치 | 검증기가 없는 것과 같다 |
| 경로 검사 실패 → 경고 후 진행 | 탈출 경로가 남는다 |

**A-1** — `C6`의 `SandboxState.UNAVAILABLE`은 실행 실패와 **별개의 값**이며
폴백이 없다 ([02. 데이터 설계 §6.8](./02-data-design.md#68-샌드박스-모델)).

### 2.3 정적 우선 (Static Before Dynamic)

**실행 없이 검사할 수 있는 것은 전부 정적으로 검사하고, 그 결과를 먼저
전달한다.**

| 표면 | 검사 방식 | 실행 필요 |
|---|---|---|
| `SKILL.md` 본문의 셸 실행 표면 | 패턴 규칙 | ❌ |
| `hooks` / `allowed-tools` | 프런트매터 검사 | ❌ |
| 스크립트의 인터프리터·의존성 | 정적 파싱 | ❌ |
| 네트워크·자격증명 접근 패턴 | 정적 패턴 | ❌ |
| **실제 동작** | 샌드박스 실행 | ✅ (opt-in) |

**A-2** — `C5` `script-analyzer`는 `scripts/` 디렉터리가 **없는** 스킬도
검사한다. 순수 마크다운 스킬이 임의 코드 실행이 가능하므로
([§7.2](#72-본문도-실행-표면이다)), 이 검사 없이는 안전한 도구라고 부를 수 없다.
`C5`는 **스파이크 `SP-1`에 의존하지 않으므로 즉시 구현 가능하다**
([04. 개발 계획 §6](./04-development-plan.md#6-단계-3--c5-script-analyzer--c6-sandbox-runner)).

### 2.4 스펙 준수 증명 (Conformance Before Features)

**스펙 규칙을 먼저 CI에서 증명하고 나서 기능을 쌓는다.**

배경: 공식 저장소는 **JSON Schema를 배포하지 않는다.** 규칙은
`skills-ref`라는 데모 라이브러리의 코드에만 존재하며, 그 라이브러리는 스스로
다음과 같이 production 용도를 거부한다 (PRD §4.3).

> *This library is intended for demonstration purposes only. It is not meant to
> be used in production.*

**A-3** — `skills-ref`를 **개발 의존성으로만** 고정하고(제약 `C3`),
동일 픽스처 코퍼스를 양쪽에 돌려 판정 일치를 CI에서 단언한다.
**의도적 불일치는 사유와 함께 명시된 목록에만 허용한다.** 이 장치의 목적은
스펙 드리프트를 **조용한 버그가 아니라 빨간 빌드**로 바꾸는 것이다.

### 2.5 인프라 선행

계약을 먼저 고정한다. `C9`가 스키마와 버전을 확정하기 전에 `C12`는
타입을 만들 수 없고, `C2`의 모델이 확정되기 전에 IPC를 설계할 수 없다.
반대로, 계약 없이 양쪽이 각자 진행하면 재계약 비용이 두 배가 된다.

**A-4** — [§5](#5-데이터-흐름)의 4개 시나리오를 경계에 먼저 정의하고
각각에 검증 명령을 붙인다.

## 3. 프로세스 아키텍처 (`C1` ↔ `C2`)

### 3.1 왜 사이드카 프로세스인가

**결정: `C2`는 별도 프로세스로 실행되는 FastAPI 사이드카다.** (`D1`, `D2`)

#### 3.1.1 Python을 코어 언어로 선택한 근거

서로 독립적인 네 가지 이유이며, **하나만 성립해도 충분하다.**

**근거 1 — 차분 테스트 패리티.** 참조 검증기 `skills-ref`는 Python이며
YAML을 **`strictyaml`**로 파싱한다. `strictyaml`은 엄격한 YAML 1.2로,
중복 키와 따옴표 안의 콜론을 거부한다 — 관대한 파서가 조용히 받아들이는
입력을. 우리 검증기가 규칙에 맞는지 증명하는 가장 이상적인 방법은
**한 프로세스에서 같은 코퍼스를 양쪽에 돌리는 것**이며, 이는 Python에서만
저렴하다. ([A-3](#24-스펙-준수-증명-conformance-before-features)의 구현 조건)

**근거 2 — 평가 계약이 Python shaped다.** `evals/evals.json`,
`grading.json`, `timing.json`, `benchmark.json`, `feedback.json`은 공식 문서의
계약이다. Pydantic v2는 판별 유니온과 정확한 JSON Schema 방출을 제공하며,
`C9`의 파이프라인이 이 방출에 의존한다 ([02. 데이터 설계 §9.5](./02-data-design.md#95-생성-파이프라인)).

**근거 3 — 에이전트 런타임 가용성.** L3 러너는 **런마다 깨끗한 컨텍스트
격리**가 필요하다. 공식 문서는 격리가 "서브에이전트를 지원하는 환경에서
자연스럽게 온다"고 설명하며(Claude Code / Agent SDK), 그렇지 않으면 별도
세션으로 얻어야 한다고 한다. 성숙한 선택지는 Python 우선이다.

**근거 4 — PEP 723은 스펙의 1급 citizen이다.** 공식 *Using scripts* 가이드는
인라인 의존성 메타데이터(`# /// script`)를 자기완결 스크립트의 권장 방식으로
내세우고 `uv run` 실행을 제시한다. 따라서 `C6` 샌드박스 러너는
`uv`/`pipx`/`npx`/`bunx`/`deno`를 **일급 citizen으로** 다뤄야 한다 — 이것은
Python 인접 툴체인이다. TypeScript로 만들면 **생태계가 문서화한 스크립트
호출 경로를 일급으로 다룰 수 없다.**

#### 3.1.2 임베디드(maturin)가 아닌 이유

| 관심사 | 사이드카 | 임베디드 (PyO3/maturin) |
|---|---|---|
| 빌드 매트릭스 | 플랫폼별 Python 휠 하나. Rust와 분리 | Rust ↔ CPython ABI 결합. Python 버전마다 재빌드 |
| **헤드리스 CI** | ✅ `pytest`가 **GUI도 Rust 빌드도 없이** 코어 전체를 실행 | ❌ 코어에 접근하려면 확장 컴파일이 선행 |
| 디버깅 반복 | ✅ 백엔드가 창과 독립적으로 재시작 | 전체 재빌드 |
| 비용 | IPC 직렬화 | 마셜링 + GIL |

결정적 요인은 **헤드리스 CI**다. `C3`·`C10`·`C11`은 90% 이상 커버리지를
요구하며(AC-5.3), 그 테스트가 Rust 빌드 없이 돌아야 한다. 코어가 GUI 빌드에
묶여 있으면 테스트 속도가 개발 속도를 결정한다.

**A-5** — IPC 세금 상환 수단: 계약이 **생성**되므로
([02. 데이터 설계 §9.5](./02-data-design.md#95-생성-파이프라인)) 손으로 쓴
직렬화 코드가 없다. 세금의 대부분이 타입 수준에서 상환된다.

#### 3.1.3 Rust를 코어로 선택하지 않은 이유

근거 4(PEP 723 / `uv` 툴체인)와 LLM 제공자·에이전트 SDK 생태계가 Python 우선
이라는 점이다. Rust로 만들면 LLM 제공자 SDK 없이 원시 HTTP로 평가 하네스를
직접 작성해야 한다.

### 3.2 프로세스 생애주기

```
[C1] 앱 기동
  │  1. 창 생성
  │  2. 사이드카 프로세스 spawn (Python 진입점, env 주입)
  │  3. stdout/stio 파이프 확보 → [전송 계층 §3.3](#33-전송-계층)에서 제어 채널로
  │  4. unix domain socket 경로 산출 → C2에 전달 (argv 또는 제어 채널)
  ▼
[C1 → C2] Handshake
  │  C2: { contractVersion, studioVersion, capabilities }
  │  C1: 검증 → 주 버전 불일치 시 명확한 오류 후 종료 (AC-5.2)
  ▼
[C1 ⇄ C2] 정상 동작
  │  unix socket 위 request/response
  │  stdio 위 이벤트 스트림 (§3.3)
  ▼
[C1] 종료
  1. C2에 shutdown 요청
  │  2. 응답 없음 시 SIGTERM → 대기 → SIGKILL
  │  3. 자식 프로세스 그룹 전체 종료 확인 (고아 방지)
  │  4. 소켓 파일 정리
  │  5. 임시 디렉터리 정리 (§9.3)
  ▼
앱 종료
```

**고아 프로세스 방지가 이 생애주기의 핵심 목적이다.** 샌드박스가 만드는
자식 프로세스(`C6`)까지 포함해 **프로세스 그룹 단위**로 종료해야 한다.
`C1`이 자식의 자식을 죽이지 못하면, 샌드박스 프로세스가 사용자 세션이
끝난 뒤에도 살아남는다.

**A-6** — `C1`은 `C6`이 스폰한 프로세스에 **추적 ID를 붙이고** 소멸 시
전부를 정리한다. 이 책임은 `C1`에만 있으며, `C2`에맡기하지 않는다.

### 3.3 전송 계층

**결정: 두 채널을 분리한다.**

| 채널 | 용도 | 특성 |
|---|---|---|
| **stdio** (stdout/stderr) | 제어-plane: 기동 핸드셰이크, 로그, 진행 이벤트 스트림 | 단방향. 프로세스 생애주기와 동일. **C2가 죽으면 끊어진다** |
| **unix domain socket** | data-plane: request/response | 양방향, 장시간 유지, 바이너리 안전 |

**왜 둘인가.** 단일 채널로 합치면 다음 문제가 생긴다.

| 문제 | 단일 채널 | 분리 |
|---|---|---|
| 이벤트와 응답의 혼선 | 스트리밍 로그가 응답 파싱을 방해 | 채널이 물리적으로 분리 |
| 파이프 소비 | `C1`이 로그를 읽지 않으면 `C2`가 **블록**된다(파이프 버퍼-full) | 이벤트 소비가 응답 지연을 유발하지 않음 |
| 진단 | 로그에 섞이면 프로토콜 오류와 섞임 | 프로토콜이 오염되지 않음 |
| Windows | 콘솔 파이프 제약 | 소켓으로 우회 |

**unix domain socket을 쓰는 이유.** 포트 할당이 없고 방화벽 프롬프트가 없다.
장시간 연결에 적합하고 바이너리 안전하다.

**Windows 주의 — `SP-2` 스파이크가 검증해야 한다.** Windows 10 1803 이후
AF_UNIX 지원이 있으나 **실제 Tauri/Rust 조합에서의 안정성은 검증되지 않았다.**
폴백은 **ephemeral 포트의 loopback TCP**다.

| 조건 | 선택 |
|---|---|
| macOS / Linux | unix domain socket |
| Windows — `SP-2` 통과 | unix domain socket |
| Windows — `SP-2` 실패 | loopback TCP (127.0.0.1, 포트 0으로 할당) |

**A-7** — 전송 계층 선택은 **플러그인화**하여 `C1`과 `C2`가 동일한
`Transport` 인터페이스만 공유하게 한다. 어느 쪽을 쓰든상위 계층은 차이를
모른다. 폴백 전환은 `C1`의 설정에 따라 자동 결정된다.

### 3.4 장애 모드

`C1`과 `C2` 사이에서 발생할 수 있는 모든 실패를 **감지 → 보고 → 복구** 순으로
정의한다. "파일을 못 읽었다" 같은 단일 오류가 아니라 경계 전체를 다룬다.

| # | 장애 | 감지 | 사용자 보고 | 복구 |
|---|---|---|---|---|
| F1 | 백엔드 크래시 | 소켓 EOF + 프로세스 종료 감지 | "코어가 응답하지 않습니다. 재시작 중…" | **자동 재시작 1회** 후 재실패 시 수동 안내 |
| F2 | 응답 없음 (무한 대기) | 요청별 타임아웃 | 어느 요청이 왜 막혔는지 | 요청만 취소, 프로세스 유지 |
| F3 | 계약 버전 불일치 | 핸드셰이크 | **양쪽 버전과 해결 방법** 명시 | 실행 거부. 업그레이드 안내 |
| F4 | 사이드카 기설 실패 | spawn 에러 / 초기 핸드셰이크 타임아웃 | 로그 경로 제시 | 수동 재시도 |
| F5 | 고아 프로세스잔류 | 종료 시 프로세스 그룹 확인 | — | 강제 종료 |
| F6 | 샌드박스 기설 실패 | `SandboxState.UNAVAILABLE` | **격리 없이 실행되지 않음**을 명시 | **오류. 폴백 없음** (A-2) |
| F7 | 디스크 공간 부족 | write 에러 | 어느 경로가 실패했는지 | 설치 중단, 이전 버전 보존 |
| F8 | LLM 어댑터 타임아웃 | 런별 타임아웃 | 부분 산출 보존 여부 명시 | 런 실패 처리, 다른 arm 계속 |

**F1은 자동 복구하고, F6은 자동 복구하지 않는다. 그 차이가 설계 의도다.**

| | F1 (코어 크래시) | F6 (샌드박스 기설 실패) |
|---|---|---|
| 사용자 데이터 | 코어에는 없다 | 샌드박스에는 사용자가 기대한 **보장**이 있다 |
| 자동 복귀 | **예 — 1회.** 재시작하면 사용자는 아무것도 잃지 않는다 | **아니오.** 자동으로 다시 시도하면 결국 무격리 실행이 될 수 있다 |
| 근거 | 가용성 | 안전성 |

**자동 재시작이 F6에 적용되었다면 논리가 뒤집힌다.** 격리 실패를
"일시적 오류"로 취급해 재시도하면, 반복 실패 뒤 사용자는 결국 **격리 없이
실행된 결과를 "안전한 결과"로 오해**하게 된다. 실패-닫힘은 예외 없이 적용한다.

**F1의 재시작은 1회로 제한한다.** 반복 재시작은 크래시 루프가 되어
사용자를 잠근다. 1회 실패 후에는 원인을 제시하고 멈춘다.

## 4. 컴포넌트 상세

각 컴포넌트는 동일 형식: 책임 / PRD 대응 / 입력 / 출력 / 의존 / **부재하는 책임**.

### 4.1 `C1` Tauri Shell

| 항목 | 내용 |
|---|---|
| **책임** | 창 수명주기, 사이드카 감독, 네이티브 다이얼로그, 권한 ACL, IPC 라우팅 |
| PRD | §4.1, §4.7 |
| **입력** | 사용자 이벤트, `C2`의 이벤트 스트림 |
| **출력** | 렌더 트리, `C2`로의 요청 |
| **의존** | `C2`(자신이 감독), `C9`(스키마) |
| **부재하는 책임** | 스펙 규칙 판단, 파일 내용 해석, 경로 결정. **절대 하지 않는다** |

**Rust 코드 예산: 800 LOC 이내(목표).** 여기에는 (a) 사이드카 생애주기,
(b) 네이티브 다이얼로그, (c) IPC 라우터만 들어간다. 도메인 로직이 들어가는
순간 §2.1이 깨지고, `C2`가 단일 진실 공급자가 아니게 된다.

**권한 모델.** Tauri v2의 capability ACL은 allowlist 기본이다. `C1`은
프런트엔드에 다음 능력만 부여한다.

| 능력 | 이유 |
|---|---|
| IPC 호출 | 필수 |
| 앱 내부 자산 읽기 | UI 번들 |
| **임의 파일 시스템 접근 없음** | 파일 접근은 전부 `C2`가 (경로 결정 권한이 `C2`에 있음) |
| **셸 실행 없음** | 프로세스 생성은 `C1`/`C2`의 내부 동작. 프런트가 직접 실행할 수 있으면 권한 경계를 우회한다 |

**A-8** — 프런트엔드에 파일 시스템 능력을 부여하지 않는다. 파일 읽기 요청은
모두 `C2`를 경유하며, `C2`는 상대 경로 식별자만 받아 절대 경로를 조립한다
([02. 데이터 설계 §9.4](./02-data-design.md#94-rpcmethod-열거형)).

### 4.2 `C2` Python Core

| 항목 | 내용 |
|---|---|
| **책임** | 모든 비즈니스 로직. 규칙의 단일 진실 공급원 |
| PRD | §4.1 |
| **입력** | 버전이 관리된 IPC 요청 |
| **출력** | 검증된 IPC 응답, 이벤트 스트림 |
| **의존** | `C3`·`C4`·`C5`·`C6`·`C7`·`C8`·`C9`·`C10`·`C11` |
| **부재하는 책임** | UI 표현. 어떤 텍스트가 화면에 어떻게 그려지는지 알지 않는다 |

`C2`는 컨테이너다. 규칙은 하위 컴포넌트가 소유하고, `C2`는 이들을
배선하고 경계를 지킨다. `C2` 안에 규칙이 직접 들어가지 않게 하는 것이
구조적 목표다.

### 4.3 `C3` `spec-core`

| 항목 | 내용 |
|---|---|
| **책임** | 스키마 정의, 프런트매터 파싱, 검증 규칙 실행, 진단 생성 (L1) |
| PRD | §4.2, §4.3 |
| **입력** | `SKILL.md` 바이트 + 스킬 루트 상대 경로 |
| **출력** | `Diagnostic` 목록, `SkillProperties`, `SkillCatalogEntry` |
| **의존** | 없음 (기초 컴포넌트) |
| **부재하는 책임** | 파일 쓰기, 실행, UI 표시. **읽기 전용이다** |

**설계 결정 4가지.**

**결정 1 — 프로필은 하나의 규칙 엔진 + 심각도 맵이다.**
`strict`(스펙 원문)와 `lenient`(실제 클라이언트가 로드하는 기준)를
**두 개의 독립 구현으로 만들면 반드시 drift한다.** 규칙은 하나이고
심각도만 프로필별로 달라진다
([02. 데이터 설계 §3.7](./02-data-design.md#37-프로필--하나의-규칙-엔진-하나의-심각도-맵)).

**결정 2 — `KeyClassification` 3분류가 필요하다.**
"미지의 키"는 하나가 아니다. 스펙 필드 / **알려진 클라이언트 확장** /
진짜 미지의 키. `skills-ref`는 후자 둘을 모두 `Unexpected fields in
frontmatter`로 보고하며(PRD §4.2), 그 결과 **정상 동작하는 Claude Code
스킬의 필드를 삭제하도록 안내한다.** 올바른 판정은
"이것은 스펙 위반이지만 이식성 문제이며, 이 클라이언트가 존중한다"와
"이것은 오타다"를 구분한다.

**결정 3 — 알려진 확장 레지스트리는 코드가 아니라 데이터다.**
클라이언트는 스펙보다 빠르게 필드를 추가한다(Claude Code만 이미 비표준
14개). 필드마다 `if` 분기를 추가하면 그 파일은 스펙 진화를 따라가지 못한다
(제약 `C14`, [02. 데이터 설계 §4.3](./02-data-design.md#43-레지스트리는-코드가-아니라-데이터)).

**결정 4 — 유니코드 `name`을 받아들인다.**
참조 구현의 문자 검사는 `c.isalnum()`이며 이는 **유니코드를 인식한다.**
`[a-z0-9-]` 하드코딩은 **틀렸고** 한국어 스킬을 거부한다. 비교는
NFKC 정규화 후 수행한다. 스펙 산문과의 불일치는 `spec_ambiguity` 진단으로
노출하고 **조용히 선택하지 않는다** ([02. 데이터 설계 §3.2](./02-data-design.md#32-name-검증-규칙--유니코드와-nfkc)).

**부재하는 책임 — 실행.** `C3`는 어떤 코드도 실행하지 않는다. 정적 분석은
`C5`의 책임이고, 경로 안전성은 `C4`의 책임이다. `C3`가 "이 스킬이 위험한가"에
대답하지 않는다. 그건 `C5`다.

### 4.4 `C4` `skill-io`

| 항목 | 내용 |
|---|---|
| **책임** | 스킬 디렉터리 입출력, 임포트 어댑터, 경로 안전성 검사 |
| PRD | §4.4 |
| **입력** | 임포트 소스(디렉터리/아카이브/git/레지스트리 API), 익스포트 대상 |
| **출력** | 스테이징 결과, `CapabilityReport` 입력용 경로 목록, **경로 안전성 판정** |
| **의존** | `C3`(strict 검증), `C5`(분석) |
| **부재하는 책임** | 실제 설치(`C11`), 경로 안전성을 통과한 파일의 배치 |

**설계 결정 2가지.**

**결정 1 — 모든 임포트는 단일 파이프라인을 지난다.**
예외 없음.

```
소스 → [STAGING] → 경로 안전성 → L1 strict → 정적 분석 → 신뢰 게이트 → 원자적 설치
```

`skills-ref`가 만든 스킬, 동료가 카피해 온 폴더, 레지스트리에서 받은 스킬이
**같은 경로를 지난다.** 검증이 회로에 정의되면 우회할 수 있다.

**결정 2 — 스테이징은 라이브 경로와 물리적으로 분리된다.**
경로 안전성 검사는 **목적지 외 어디에도 쓰지 않은 상태로** 완료되어야 한다.
그렇지 않으면 "검사"가 "설치 후 확인"이 되어 의미가 사라진다
([02. 데이터 설계 §10.1](./02-data-design.md#101-임포트-파이프라인)).

**부재하는 책임 — 신뢰 판단.** `C4`는 위험을 **보고**하지만 설치 여부를
**결정하지 않는다.** 그건 사람이다(`O3` 신뢰 게이트). 자동 승인은
`C4`의책임 밖이다.

### 4.5 `C5` `script-analyzer`

| 항목 | 내용 |
|---|---|
| **책임** | 스킬 **전체**의 실행 표면 정적 탐지 |
| PRD | §4.5 |
| **입력** | 스킬 루트(상대 경로) |
| **출력** | `CapabilityReport` |
| **의존** | `C3`(프런트매터 재사용) |
| **부재하는 책임** | **실행.** 어떤 코드도 실행하지 않는다 |

**설계 결정 3가지.**

**결정 1 — 본문도 실행 표면이다.** [§7.2](#72-본문도-실행-표면)에서 상술.
`scripts/`만 보면 놓친다.

**결정 2 — 분석기는 파일 바이트의 순수 함수다.**
쓰지 않고, 읽지 않고(스킬에 대해), 실행하지 않고, 결정적이다. 이 순수성
때문에 **악의적 픽스처로철저히 테스트**할 수 있다 — "이 페이로드가 탐지되는가"
를 실제 실행 없이 검증한다
([02. 데이터 설계 §6.6](./02-data-design.md#66-분석기의-순수성)).

**결정 3 — 정보 신호와 위험 신호를 같은 톤으로 표시하지 않는다.**
`declared_dependency`(의존성 12개)는 위험이 **아니다.** 위험 신호와 정보
신호가 같은 비중으로 표시되면 **신뢰 게이트 전체가 무효화**된다. 안전한
스킬은 "실행 표면 없음"을 **긍정 신호**로 표시한다.

**부재하는 책임 — "안전"의 최종 판단.** `C5`는 발견 사항을 낸다.
"이 스킬을 설치해도 되는가"는 사람이 답한다.

### 4.6 `C6` `sandbox-runner`

| 항목 | 내용 |
|---|---|
| **책임** | 격리된 스크립트 동적 실행 (opt-in, 기본 OFF) |
| PRD | §4.5, §9 (SP-1) |
| **입력** | 스크립트 상대 경로, 인자, `SandboxProfile` |
| **출력** | `SandboxRunResult` |
| **의존** | 없음 (실행 환경) |
| **부재하는 책임** | **어떤 스크립트를 실행할지 고르는 것** |

**설계 결정 2가지.**

**결정 1 — 기본 OFF + 실패-닫힘.** 데스크톱 앱이 사용자 권한으로
받은 코드를 실행하는 것은 **악성코드 전달 경로**가 된다. 그래서
기본을 끄고, 사용자 명시 동의 없이는 실행하지 않는다. 그리고
격리 실패 시 **오류**로 끝낸다 (A-2).

**결정 2 — v1에서 LLM 주도 자동 실행을 제외한다.**
LLM이 스스로 어떤 스크립트를 실행할지 고르는 루프는 v1 범위 밖이며
(PRD §4.5), 실제 적대적 안전성 검토가 필요한 컴포넌트다. v1은
**사용자가 고른 스크립트를 사용자가 준 인자로** 실행한다. 이 축소는
정직한 축소다.

**부재하는 책임 — 위험 분석.** `C6`는 `C5`의 발견을 입력으로 받지 않는다.
`C6`는 격리를 실행하고, 판단은 `C5`와 사람이 한다.

### 4.7 `C7` `eval-engine`

| 항목 | 내용 |
|---|---|
| **책임** | L3 평가 루프 오케스트레이션: A/B 실행, 채점, 집계, 분석 |
| PRD | §4.6 |
| **입력** | `EvalSuite`, 스킬 디렉터리, `RunAdapter` |
| **출력** | 워크스페이스 트리, `Grading`, `Benchmark`, `AssertionAnalysis` |
| **의존** | `C8`(어댑터), `C3`(프런트매터) |
| **부재하는 책임** | 모델 호출 자체, 채점 규칙의 정의 |

**설계 결정 4가지.**

**결정 1 — 공식 디스크 계약을 바이트 호환으로 생성한다.**
공식 문서를 따라 작성된 스킬이 **변환 없이** 동작해야 한다. 컨벤션을
우리가 스스로 만들면 스킬 저자가 변환기를 써야 한다.

**결정 2 — A/B 실행은 강제된다.** 한 번의 실행은 결과가 아니다.
**차이야 결과다.** 케이스가 `with_skill`만 실행되었다면 그것은 불완전한
측정이며 `C7`은 이를 명시적으로 경고한다
([02. 데이터 설계 §7.2](./02-data-design.md#72-armname--세-가지-arm)).

**결정 3 — 결정론적 체커가 LLM 판정보다 먼저다.**
공식 문장이 명시한다: *"코드로 검사할 수 있는 것에는 검증 스크립트를 써라.
스크립트가 LLM 판단보다 기계적 검사에 더 신뢰할 만하다"*(PRD §4.6).
이 순서는 **테스트로 증명 가능**하다 — 판정 어댑터의 호출 카운터가 0인지
단언한다 (AC-2.8). 순서가 뒤집히면 즉시 실패한다.

**결정 4 — `n < 2`이면 표준편차를 계산하지 않는다.**
`stddev`는 `None`이다. **0.0이 아니다.** 0.0은 "편차가 없다"를 주장하므로
단일 실행에서 오해를 만든다. 공식 문서도 이 점을 명시적으로 경고한다.

**부재하는 책임 — 채점 기준의 정의.** `C7`은 assertion을 받아 판정한다.
**어떤 기준이 좋은 assertion인지는 사람이 정한다** — 그래서 `feedback.json`이
일급 citizen이다.

### 4.8 `C8` `RunAdapter`

| 항목 | 내용 |
|---|---|
| **책임** | L3 제공자 중립 실행 seam |
| PRD | §4.6, G5 |
| **입력** | `RunRequest` |
| **출력** | `ArmResult` |
| **의존** | 외부 LLM 제공자 |
| **부재하는 책임** | 채점, 집계, 스킬 해석 |

**설계 결정 2가지.**

**결정 1 — 프로토콜 경계이지 분기가 아니다.**
`if provider ==` 형태의 분기가 들어가면 G5(제공자 중립)가 깨진다.
표준 자체가 제공자 중립이므로 스튜디오도 그래야 한다.

**결정 2 — `AdapterCapabilities`로 보고 가능 범위를 선언한다.**
제3의 어댑터가 `total_tokens`를 보고하지 못할 수 있다. `None`으로 넣으면
"0토큰"과 "미보고"가 구별되지 않는다. **0이 아닌 `None`이 정직한 값**이다.

**`MockAdapter`가 이 절의 설계 중심이다.** 네트워크·API 키 없이
**전체 파이프라인을 결정적으로** 돌려야 AC-2.6이 성립한다. 이것이
가능해야 평가 엔진의 나머지를 자유롭게 리팩터링할 수 있다.

### 4.9 `C9` `ipc-contract`

| 항목 | 내용 |
|---|---|
| **책임** | 계약 정의, JSON Schema 방출, TS 타입 생성, 버전 관리 |
| PRD | §4.7 |
| **입력** | Pydantic 모델 (진실 공급원) |
| **출력** | JSON Schema, 생성된 TS 타입, `Handshake` |
| **의존** | Pydantic |
| **부재하는 책임** | 전송 구현. 전송은 `C1`/`C2`의 책임 |

**설계 결정 3가지.**

**결정 1 — Pydantic이 유일한 진실 공급원이다.** JSON Schema와 TS 타입은
**생성물**이며 손으로 편집하지 않는다
([02. 데이터 설계 §11.1](./02-data-design.md#111-진실-공급원과-파생물)).

**결정 2 — 경계 양방향 검증이 필수다.** 내부 모델이 검증 없이 wire를
넘는 경로가 있으면 안 된다. 그 경로 하나가 `D-4`를 무효화한다.

**결정 3 — 주 버전을 호환 경계로 삼는다.** 부 버전은 추가 가능(호환),
주 버전은 파괴적. 제약 강화는 `major`다 — 이전에 통과하던 스킬이
실패할 수 있으므로 조용히 더 엄격해지면 안 된다
([02. 데이터 설계 §11.4](./02-data-design.md#114-스키마-버전과-하위-호환)).

### 4.10 `C10` `packager`

| 항목 | 내용 |
|---|---|
| **책임** | 결정적 아티팩트 생성, `manifest.json` |
| PRD | §4.8 |
| **입력** | 스킬 디렉터리 |
| **출력** | `.tar.gz` + 외부 `manifest.json` |
| **의존** | `C3`(최종 검증) |
| **부재하는 책임** | 설치(`C11`), 서명 |

**설계 결정 2가지.**

**결정 1 — 포맷은 결정적 tar.gz다.** ZIP은 mtime·권한 통제가 약하고,
OCI/npm은 이 형식이 필요로 하지 않는 **리졸버와 레지스트리 의존성**을
도입한다. 스킬은 디렉터리이고 스펙은 배포 포맷을 정의하지 않는다.

**결정 2 — 재현성은 테스트로 증명한다.**
**재현성을 테스트하지 않으면 재현성은 주장이지 기능이 아니다.**
두 번 빌드해 다이제스트를 비교한다 (AC-3.1).

**부재하는 책임 — 신원 보증.** `manifest.json`은 해시를 제공하지만
**서명하지 않는다.** 서명은 v2 범위다.

### 4.11 `C11` `installer`

| 항목 | 내용 |
|---|---|
| **책임** | 대상 경로 결정, 우선순위·섀도잉 처리, 원자적 설치/제거, 가시성 검증 |
| PRD | §4.9 |
| **입력** | `SkillProperties`, `ClientKind`+scope (경로는 `C2`가 조립) |
| **출력** | `InstallPlan`, `InstallOutcome`, `VisibilityReport` |
| **의존** | `C3`(목적지에서 재검증), `C10`(아티팩트) |
| **부재하는 책임** | 위험 판단(`C5`), 사용자 승인(`C12`) |

**설계 결정 2가지.**

**결정 1 — "설치 성공"의 정의는 "클라이언트가 찾는다"다.**
"바이트를 썼다"가 아니다. 설치 후 실제 클라이언트와 동일한 탐색을
**재현**하고 `VisibilityReport`를 만든다. `found=false`면 실패다.

**결정 2 — 원자성은 임시 디렉터리 + 검증 + rename이다.**
실패 시 이전 버전이 온전하고 라이브 경로는 무변경이다 (AC-3.5).

**부재하는 책임 — 조용한 선택.** `C11`은 **우선순위 충돌에서 스스로
승자를 고르지 않는다.** 경고를 낸다 (AC-3.7).

### 4.12 `C12` UI Layer

| 항목 | 내용 |
|---|---|
| **책임** | 표현, 상태 관리, 사용자 입력 수집 |
| PRD | §4.1, §6 (AC-6) |
| **입력** | 검증된 IPC 응답, 이벤트 스트림 |
| **출력** | 렌더 트리, IPC 요청 |
| **의존** | `C9`(생성된 타입) |
| **부재하는 책임** | **규칙 재구현.** 경로 결정. 신뢰 판단 |

세부 설계는 [03. UI 디자인](./03-ui-design.md)이 소유한다.
이 문서는 `C12`의 **경계만** 규정한다.

## 5. 데이터 흐름

네 개 핵심 시나리오. 각 흐름의 경계가 계약이므로, 경계를 흐르는 값은
**모두 경계에서 검증**된다 (`D-4`).

### 5.1 시나리오 ① — 스킬 검증

```
사용자 입력 (타이핑)
   │
   ▼
[C12] CodeMirror 6 편집 버퍼
   │  디바운스 300ms
   ▼
[C12] spec.validate(relpath, text)          ← 상대 경로만 전송
   │
   ▼ (unix socket)
[C2] C9 경계 검증 → C3
   │
   ├─ 파서: 프런트매터 분리 (§5.1 of 데이터설계)
   ├─ 검증: 규칙 엔진 + 심각도 맵
   └─ 결과: Diagnostic[]
   │
   ▼
[C12] 세 갈래로 렌더
   ├─ gutter squiggle  (span → CM6 decoration)
   ├─ DiagnosticsPanel (필터 · 그룹 · 점프)
   └─ 상태 바 (error/warn 개수)
```

**경계에서 검증되는 것**: `relpath`는 상대 경로여야 한다. 절대 경로는
클라이언트가 보낼 수 없다 (§3.4 A-8).

### 5.2 시나리오 ② — L3 평가 실행

```
사용자: [S4] 실행
   │
   ▼
[C12] eval.run(skillId, caseIds[], armNames[], repeats)
   │
   ▼
[C2] C7
   │
   ├─ EvalSuite 로드 + 검증
   ├─ ArmName별 × 반복수만큼 실행 계획 생성
   │
   ├─ 각 런: C8.run(RunRequest)
   │     └─ [외부] LLM 제공자 (격리된 세션)
   │     └─ ArmResult { outputs, timing, skill_auto_activated }
   │
   ├─ 채점 파이프라인
   │     ├─ 1단계 결정론적 체커 (LLM 미호출)
   │     └─ 2단계 LLM 판정 (남은 것만, 증거 강제)
   │
   ├─ Benchmark 집계 (n<2 → stddev=None)
   ├─ AssertionAnalysis 4종
   └─ 워크스페이스 트리 기록
   │
   ▼ StreamEvent (stdio)
[C12] TestRunnerView  ─ 스트리밍 로그 · 진행 · arm 비교
   │
   ▼ 완료
[C12] ReportView ─ 채점표(증거) · benchmark · 4종 분석 · feedback 편집기
```

**취소 경로**: `eval.cancelRun`은 진행 중인 런에 취소 신호를 보내고
**부분 산출을 보존**한다 (F8). 디버깅 가능성을 남긴다.

### 5.3 시나리오 ③ — 임포트

```
사용자: [S8] 소스 선택 (폴더/아카이브/git/레지스트리)
   │
   ▼
[C2] C4 — STAGING (임시 디렉터리로 복사)
   │      ⚠ 라이브 경로에 아무것도 쓰지 않는다
   ▼
[C2] C4 — 경로 안전성 검사
   │   .. · 절대경로 · 탈출 심볼릭 링크 · 크기/개수 상한 · setuid
   │   └─ 실패 → 즉시 거부 (확인으로 우회 불가)
   ▼
[C2] C3 — strict 검증
   │   └─ error 존재 → 설치 금지
   ▼
[C2] C5 — 정적 분석
   │   CapabilityReport (실행 표면 · 의존성 · 위험 신호)
   ▼
[C2] C11 — InstallPlan 생성 (dry-run)
   │   blockers · warnings · shadowed_by · reserved_name
   ▼
[C12] O3 신뢰 게이트 ─ 사용자 명시적 동의
   │   · strict 오류 목록
   │   · 분석 발견 사항
   │   · "description은 모든 미래 세션의 카탈로그에 주입된다"
   ▼
[C2] C11 — 원자적 설치
   │   형제 임시 디렉터리 → 목적지 재검증 → atomic rename
   ▼
[C2] C11 — VisibilityReport (탐색 재현)
   ▼
[C12] 결과: "설치됨 — 클라이언트가 찾음" / "설치됨 — 그러나 로드되지 않음"
```

### 5.4 시나리오 ④ — 패키징 → 설치

```
사용자: [S6] 패키지 빌드
   │
   ▼
[C12] package.preview(skillId)  ─ 재현성 고정 파라미터 표시
   │
   ▼
[C2] C10 — 결정적 빌드
   │   경로 정렬 · mtime 고정 · uid/gid=0 · 모드 정규화
   │   ACL/xattr 제거 · gzip 고정 레벨 · 심볼릭 링크 제외
   ▼
[C2] C10 — manifest.json (아카이브 외부)
   │   파일별 sha256 + TreeDigest
   ▼
[C2] C11 — install.plan(artifact)
   │   대상 경로 선택 → 계획 제시
   ▼
[C12] 승인 → [C2] C11 원자적 설치 → VisibilityReport
```

## 6. 프로세스 간 배치

```
[OS]
 ├─ C1 Tauri 프로세스
 │   ├─ WebView (C12 렌더러)  ← 파일 시스템 능력 없음
 │   └─ C2 사이드카 프로세스
 │        ├─ C3 spec-core
 │        ├─ C4 skill-io
 │        ├─ C5 script-analyzer
 │        ├─ C6 sandbox-runner ─→ 샌드박스 자식 프로세스(들)
 │        │                          ↑ 프로세스 그룹으로 종료 추적 (A-6)
 │        ├─ C7 eval-engine ─────→ C8 RunAdapter ─→ 외부 LLM (네트워크)
 │        ├─ C9 ipc-contract
 │        ├─ C10 packager
 │        └─ C11 installer ──────→ ~/.agents/skills/ 등 라이브 경로
 │
 ├─ 스테이징 임시 디렉터리 (임포트 중, 라이브와 격리)
 └─ 평가 워크스페이스 <skill>-workspace/iteration-N/
```

**네트워크 전이점 두 곳만 존재한다.**

| 지점 | 대상 | 통제 |
|---|---|---|
| `C8` | 외부 LLM API | 사용자 동의 + 자격증명는 OS 키체인에. 스킬에 넣지 않는다 |
| `C4` | git / 레지스트리 | 스킬 경로와 무관한 외부 입력. 경로 안전성 검사 대상 |

**`C6`의 샌드박스는 네트워크를 차단한다** (기본). 따라서 **샌드박스가 실제로
성립했을 때** 실행되는 스킬 코드에는 외부로 나가는 경로가 없다. 이 성질이
샌드박스의 존재 이유이며, `SP-1`이 검증해야 하는 첫 번째 항목이다.

> ⚠ **아직 확인되지 않았다.** 위 성질은 `SandboxProfile`의 **설계 의도**이지
> **검증된 결과**가 아니다. `SP-1`의 탈출 테스트가 통과하기 전까지
> "네트워크가 차단된다"고 말할 수 없다. `A-O-2`는 이 미확인 상태를 추적한다.

## 7. 보안 아키텍처

### 7.1 신뢰 경계 3개

```
        ┌──────────── 신뢰 경계 ①: 사용자 로컬 파일 시스템 ────────────┐
        │  사용자가 직접 만들거나 선택한 콘텐츠 → 신뢰                  │
        │  C1 자체 코드, C2 자체 코드, 사용자가 편집 중인 SKILL.md      │
        └───────────────────────┬──────────────────────────────────────┘
                                │ 경계를 넘어감
        ┌───────────────────────▼──────────────────────────────────────┐
        │           신뢰 경계 ②: 임포트되는 외부 콘텐츠                  │
        │  출처를 신뢰할 수 없는 코드와 텍스트                           │
        │  아카이브, git 저장소, 레지스트리 스킬, 동료의 사본             │
        └───────────────────────┬──────────────────────────────────────┘
                                │ 경계를 넘어감
        ┌───────────────────────▼──────────────────────────────────────┐
        │              신뢰 경계 ③: 실제로 실행되는 코드                  │
        │  스킬의 번들 스크립트, 본문의 셸 실행 표면                      │
        └──────────────────────────────────────────────────────────────┘
```

| 경계 | 통과하는 것 | 통제 수단 |
|---|---|---|
| ① | 사용자가 만든 콘텐츠 | 사용자의 판단. 자동화 없음 |
| ② | 외부 스킬 | **정적 분석 + 경로 안전성 + 신뢰 게이트** (전부 필수) |
| ③ | 실행 코드 | **샌드박스(실행 전) + 정적 분석(실행 전)** |

**핵심: ②와 ③의 통제 수단은 모두 "실행 전"이다.** 샌드박스는 ③의 사후
통제지만, ②에서 정적 분석으로 ③에 도달할 가능성을 먼저 낮춘다. 이 순서가
A-3(정적 우선)의 근거다.

### 7.2 본문도 실행 표면이다

**이것이 §2.3이 존재하는 이유이며, 이 프로젝트에서 가장 중요한 보안 발견이다.**

Claude Code의 *Inject dynamic context* 문서는 `SKILL.md` 본문의
`` !`<command>` `` 플레이스홀더가 **스킬 내용이 모델에게 전달되기 전에
셸 명령을 실행**하고, 그 출력을 해당 자리에 치환한다고 명시한다. 여러 줄은
`` ```! `` 펜스 블록으로 같은 일을 한다 (PRD §4.5).

**결과: `scripts/` 디렉터리가 전혀 없는 순수 마크다운 스킬이 임의 코드
실행이 가능하다.**

| 흔한 오해 | 실제 |
|---|---|
| "텍스트 파일이니 안전하다" | 본문이 셸 명령을 실행한다 |
| "실행 표면은 `scripts/`뿐이다" | 본문에도 있다. 더 놀랍게도 |
| "스킬을 사용 안 하면 아무 일도 없다" | `description`은 **모든 세션**에서 주입된다 (§7.4) |

**통제 수단과 그 한계.**

| 수단 | 제공자 | 스킬 작성자가 통제 가능한가 |
|---|---|---|
| `disableSkillShellExecution` 설정 | **호스트 정책** | ❌ 아니오. 작성자가 설정할 수 없다 |
| claude.ai 동기화 스킬은 비실행 | Claude Code | 해당. 로컬 서드파티 스킬은 해당 없음 |
| `C5` 정적 분석 | **스튜디오** | ✅ 제공한다 |

**로컬 서드파티 스킬은 앞의 두 보호를 모두 받지 못한다.** 그래서
`C5`의 본문 검사는 기본 ON 경로에 있고, 실행 표면이 하나도 없는 스킬은
"실행 표면 없음"을 긍정 신호로 표시한다
([02. 데이터 설계 §6.5](./02-data-design.md#65-안전-신호의-표현)).

### 7.3 인라인 플레이스홀더의 정확한 탐지 규칙

과다 탐지는 신뢰를 파괴한다. 규칙을 정확히 인코딩한다.

| 입력 | 실행 | 분석기의 판정 |
|---|---|---|
| `` !`git diff HEAD` `` | ✅ | `body_shell_exec` (DANGEROUS) |
| ``` - diff: !`gh pr diff` ``` | ✅ | `body_shell_exec` (DANGEROUS) |
| ``KEY=!`cmd` `` | ❌ | **판정 안 함.** 리터럴 텍스트 |
| `a!`cmd`` | ❌ | **판정 안 함** |

그리고 대체는 **원본 파일에 대해 1회만** 수행되므로, 명령 출력이 추가
플레이스홀더를 만들어도 전이적으로 확장되지 않는다.

**A-9** — `!`만 찾는 단순 패턴을 쓰지 않는다. `(?<=\s)|^` 조건이 없으면
`KEY=!`cmd``에서 오탐이 나고, 그 오탐이 "이 도구는 시끄럽다"는 인상을 준다.
또한 이 규칙을 **도구의 설명에 명시**한다 — 사용자가 "내 스킬이 왜 위험하다고
여겨지는지"를 이해해야 한다.

### 7.4 컨텍스트 인젝션 표면

**`description`은 모든 미래 세션의 카탈로그에 무조건 주입된다.**

점진적 공개의 티어 1은 설치된 **모든** 스킬의 `name`과 `description`을
세션 시작 시 로드한다 — 스킬당 대략 50–100 토큰
(PRD §4.2, 공식 client-implementation 가이드).

**따라서 악의적인 `description`은 스킬이 한 번도 활성화되지 않아도 지속되는
인젝션 벡터**다. 공식 가이드도 이에 상응하는 점을 지적한다 — 신뢰하지 않는
저장소에서 오는 프로젝트 레벨 스킬이 사용자 동의 없이 에이전트 컨텍스트에
주입될 수 있다.

**이 성질은 두 곳에서 사용자에게 노출한다.**

| 위치 | 표현 |
|---|---|
| `O3` 신뢰 게이트 | "이 스킬의 `description`은 이후 모든 세션의 카탈로그에 주입됩니다" (AC-4.5) |
| `S2` 편집기 | 프런트매터 `description` 필드 옆에 상시 힌트 |

**A-10** — `description`의 길이와 내용에 대한 권고(`weak_description`,
`truncation_risk`)를 **`C3`가 `C5`와 함께** 제공하므로, 인젝션 위험을
"설치 시점의 한 번"이 아니라 **작성 중**에 줄일 수 있다.

### 7.5 방어 계층 3단계

```
        ┌─────────────────────────────────────────────────────┐
        │ 1단계: 정적 분석 (C5) — 기본 ON, 실행 없음           │
        │   본문 실행 표면 · 훅 · 도구 승인 · 의존성            │
        │   네트워크 · 자격증명 · FS 탈출                       │
        └──────────────────────────┬──────────────────────────┘
                                   │ 발견 사항
        ┌──────────────────────────▼──────────────────────────┐
        │ 2단계: 신뢰 게이트 (O3) — 사람의 결정                 │
        │   strict 오류 있으면 설치 금지                       │
        │   위험 발견 있으면 명시적 동의 필요                 │
        │   기본 거부. 확인으로 경로 안전성 실패는 우회 불가    │
        └──────────────────────────┬──────────────────────────┘
                                   │ 동의
        ┌──────────────────────────▼──────────────────────────┐
        │ 3단계: 샌드박스 (C6) — opt-in, 기본 OFF, 실패-닫힘   │
        │   네트워크 차단 · FS read-only · 비-root             │
        │   자원 상한 · 전체 출력 보존                          │
        └─────────────────────────────────────────────────────┘
```

| 층 | 활성화 | 실패 시 |
|---|---|---|
| 1 정적 | 항상 | 분석 실패를 "안전"으로 표시하지 않는다 |
| 2 게이트 | 항상 | 거부 |
| 3 샌드박스 | 사용자 선택 | **오류. 폴백 없음** |

**A-11** — 분석 자체가 실패한 경우(`analysis_complete=false`)를
"발견 사항 없음"과 구별한다. **분석 실패는 안전이 아니다**
([02. 데이터 설계 §6.5](./02-data-design.md#65-안전-신호의-표현)).

### 7.6 `C6` 격리 제어

| 제어 | 강제 방법 | 위반 시 |
|---|---|---|
| 네트워크 | 기본 차단. 명시적 동의 시 화이트리스트 | 실행 거부 |
| 파일 시스템 | 스킬 디렉터리 read-only 마운트, 출력은 `tmpfs` | 실행 거부 |
| 홈 디렉터리 | 접근 불가 | 실행 거부 |
| 신원 | 비-root UID, 보조 그룹 없음, capability 제거 | 실행 거부 |
| 자원 | 벽시계 타임아웃, 메모리/CPU/PID 상한 | 강제 종료 |
| 프로세스 | `--privileged` 없음, 호스트 디바이스 없음, Docker 소켓 없음 | 실행 거부 |
| 관측 가능성 | 전체 stdout/stderr 캡처, 런과 함께 보존 | — |

**SP-1 스파이크가 검증하는 것은 이 표가 실제로 성립하는지다.** 특히
"일반 개발자 노트북에서"라는 조건이 붙는다. Docker 29.8.1이 **개발
환경에 존재함**을 확인했으므로 컨테이너 경로는 현실적이다. 그러나
**사용자의 목표 머신에 Docker가 없을 수 있다**는 조건은 남는다
([04. 개발 계획 §2](./04-development-plan.md#2-단계-개요-stage-map)에 분기 결정 기록).

### 7.7 v1에서 제외한 보안 범위

| 제외 항목 | 이유 |
|---|---|
| LLM 주도 스크립트 자동 실행 | 적대적 안전성 검토가 필요하다. v1은 사용자가 고른 스크립트만 실행 |
| 아티팩트 서명 | `manifest.json`은 해시를 주지만 신원을 보증하지 않는다. v2 |
| 레지스트리 신뢰 체인 | v1은 로컬 설치만 (D4) |
| `metadata`의 실행 가능 값 | 스펙이 `str→str`만 허용하므로 실행 표면이 없다 |

## 8. 설치 타깃 아키텍처 (`C11`)

### 8.1 대상 경로

[02. 데이터 설계 §8.4](./02-data-design.md#84-installtarget--clientkind)의 매트릭스가
경로를 정의한다. 아키텍처 관점의 결정만 여기 기록한다.

| 결정 | 근거 |
|---|---|
| 기본 추천 대상은 `AGENTS`(`.agents/skills/`) | 공식 가이드가 크로스 클라이언트 상호운용 규약으로 명시 |
| `PROJECT`와 `USER`를 모두 지원 | 프로젝트 공유와 개인 사용이 다른 요구다 |
| 클라이언트별 경로를 **표로 관리** | 하드코딩된 경로 목록은 새 클라이언트 추가 시 깨진다 |
| **어떤 경로도 하드코딩하지 않는다** | `C4` `ClientKind` → 경로 변환 테이블이 유일한 진실 |

### 8.2 우선순위와 충돌

공통 규약은 **프로젝트 레벨이 사용자 레벨을 덮어쓴다** (PRD §4.9).

**A-12** — `C11`은 충돌에서 **승자를 고르지 않는다.** 경고를 낸다
(AC-3.7). 조용히 선택하면 사용자는 "내 스킬이 왜 안 먹히지"를 추적할 수 없다.
섀도잉은 `VisibilityReport`에 `is_shadowed`와 `shadowing_source`로 기록되어
**설치 시점에** 사용자에게 보인다.

### 8.3 "설치 성공"이 거짓말이 되는 4가지 경우

| 경우 | 규칙 | 근거 |
|---|---|---|
| **예약 이름** | `synced`·`anthropic-skills`·`anthropic-skills:*` → **차단** | 조용히 로드되지 않는다 (PRD §4.9) |
| **`synced/` 소유권** | `~/.claude/skills/synced/`에 쓰지 않는다 | claude.ai 동기화 전용. 로컬 편집은 덮어써지고 수동 삭제는 재다운로드된다 |
| **플러그인 폴더** | `.claude-plugin/plugin.json` 보유 시 플러그인으로 로드 | 신뢰 대화상자가 선행된다. 설치만으로는 활성화되지 않는다 |
| **부모 탐색** | 프로젝트 스킬은 시작 디렉터리 **와 모든 부모**에서 로드 | 모노레포에서 검증 위치가 실제 세션 위치와 다를 수 있다 |

**예약 이름을 차단하는 이유 (기본값 선택).** 경고만 남기면 사용자는
"설치는 됐는데 왜 안 되지"를 풀지 못한다. 되돌릴 수 없는 상태로 남는다.
차단하고 이름을 바꾸는 경로를 제시한다 — reversible하다.
`reserved_name` 진단이 `quick_fix`를 제공한다
([02. 데이터 설계 §8.5](./02-data-design.md#85-installplan과-가시성)).

**A-13** — 심볼릭 링크의 신뢰 비대칭이 **세 곳에서 다르다**는 점을
명시한다: 로컬 스캔은 **추종**(사용자 설정), 아카이브 임포트는 **거부**
(공격자 공급), 패키징은 **제외**(재현성). 근거는 하나 — **출처 신뢰도**다.
하나의 규칙으로 합치면 합법적 설치를 깨거나 트래버설을 허용한다 (제약 `C16`).

## 9. 운영 · 배치

### 9.1 레이어별 구성

`C1`과 `C12`은 **번들**되고, `C2`는 **번들에 포함된 인터프리터 또는
지시 설치**로 배포된다.

| 결정 | 근거 |
|---|---|
| 배포 단위는 앱 하나 | 사이드카가 별도 설치면 "앱이 안 뜬다"의 원인이 곱해진다 |
| `C2` 의존성은 **번들에 번들**한다 | `uv`로 동일 버전 고정 (제약 `C6`의 언어 선택과 동일한 도구) |
| 마이그레이션 | v1은 사용자 데이터가 디스크에 있으므로 **스키마 마이그레이션이 불필요**하다. 캐시만 폐기한다 |

**`C2` 의존성 동봉의 이유.** `uv`로 파이썬 버전을 고정해야 샌드박스가
 predictability를 갖는다. 사용자 머신의 시스템 파이썬에 의존하면
버전 차이로 검증 결과가 달라진다.

### 9.2 캐시

[02. 데이터 설계 §1.3](./02-data-design.md#13-저장-계층-전략--스튜디오는-자체-데이터베이스를-갖지-않는다)에서
정한 원칙을 따른다. 캐시는 **재구축 가능해야 하고 정답이 아니다.**

| 캐시 | 내용 | 무효화 |
|---|---|---|
| 카탈로그 인덱스 | `name`·`description`·`relpath` | 파일시스템 이벤트 + 버전 스탬프 |
| 검증 결과 | `relpath` → `Diagnostic[]` | 파일 내용 변경 |
| 어댑터 응답 | 없음 (캐시하지 않음) | — |

**A-14** — 파일시스템 이벤트는 **최적화일 뿐 유일한 근거가 아니다.**
이벤트를 놓칠 수 있으므로, 캐시 사용 시 반드시 **스탬프 비교**로 검증한다.
이벤트만 믿으면 오래된 검증 결과를 사용자에게 보인다.

### 9.3 임시 디렉터리

| 용처 | 수명 | 정리 책임 |
|---|---|---|
| 임포트 스테이징 | 임포트 1회 | `C4`. 완료·실패 모두 |
| 샌드박스 출력 | 샌드박스 실행 1회 | `C6`. 런 보존 정책에 따름 |
| git 얕은 복제 | 임포트 1회 | `C4` |
| **평가 워크스페이스** | **영구** | **정리하지 않는다** |

**평가 워크스페이스를 지우지 않는 이유.** 그것이 사용자의 결과물이다.
반복 간 비교(`iteration-1` vs `iteration-2`)가 이 도구의 목적이며,
`C7`은 이전 반복을 덮어쓰지 않는다
([02. 데이터 설계 §7.11](./02-data-design.md#711-워크스페이스-레이아웃)).

**A-15** — 앱 종료 시 임시 디렉터리를 정리하되 **평가 워크스페이스는
제외**한다. 종료 정리와 보존 대상의 경계를 명시적으로 코드로 남긴다.

## 10. 검증

이 문서의 각 결정이 **어느 테스트로 증명되는가.** 구현 단계의 배치는
[04. 개발 계획 §10](./04-development-plan.md#10-추적성-매트릭스)이 소유한다.

| 결정 | 검증 방법 | AC |
|---|---|---|
| §2.1 규칙의 단일 진실 공급원 | TS에 스펙 규칙 문자열이 없음을 grep으로 단언. 규칙은 Pydantic에만 존재 | AC-5.1 |
| §2.1 Rust에 도메인 로직 없음 | `src-tauri` LOC 카운트 상한 검사 + 도메 규칙 키워드 부재 검사 | — |
| §3.2 고아 프로세스 없음 | 종료 후 자손 프로세스 존재 여부 단언 (샌드박스 포함) | — |
| §3.3 전송 계층 교체 가능 | 폴백 모드로도 같은 계약 테스트 통과 | — |
| §3.4 F3 계약 불일치 | 불일치 시 명확한 오류 메시지 + 거부 | AC-5.2 |
| §4.3 프로필이 한 엔진 | 두 프로필이 같은 `DiagnosticCode` 집합을 쓰는지 단언 | AC-1.5 |
| §4.3 확장 3분류 | 확장 필드와 미지 키가 **다른 코드**를 내는지 단언 | AC-1.3a |
| §4.3 유니코드 이름 | 한국어 이름이 `name_charset`를 내지 않음 | AC-1.4 |
| §4.5 본문 실행 표면 탐지 | `scripts/` 없는 픽스처가 탐지됨 | AC-2.1a |
| §5.2 결정론적 우선 | 판정 어댑터 호출 카운터 0 | AC-2.8 |
| §5.2 `n<2` 표준편차 없음 | `stddev is None` | AC-2.7 |
| §6 샌드박스 네트워크 차단 | 네트워크 유출 시도 스크립트가 실패 | AC-2.2 |
| §2.2 실패-닫힘 | 샌드박스 부재 시 실행 시도 → 오류 | AC-2.3 |
| §7.4 인젝션 경고 문구 | `O3` 문구에 카탈로그 주입 명시 포함 | AC-4.5 |
| §8.2 섀도잉 경고 | 충돌 시 경고 발생, 자동 선택 없음 | AC-3.7 |
| §8.3 가시성 검증 | 설치 후 `found=false`면 실패로 보고 | AC-3.6 |
| §9.2 캐시 스탬프 | 이벤트 없이 파일 변경 시 캐시 무효화 | — |

**자동으로 증명할 수 없는 것.** §7.6의 격리 강제는 **SP-1 스파이크의 실측
대상**이며, 단위 테스트로 증명할 수 없다. 네트워크 차단이 진짜로 되는지는
**탈출을 시도하는 스크립트를 실제로 돌려봐야** 알 수 있다. 이 문서는
그 사실을 명시하며, SP-1이 통과하지 못하면 v1 범위를 정직하게 축소한다
([04. 개발 계획 §3](./04-development-plan.md#3-단계-0--스파이크)).

## 11. 열린 이슈

| ID | 이슈 | 영향 | 처리 |
|---|---|---|---|
| `A-O-1` | **Windows의 unix domain socket 미검증** | 전송 계층 선택이 플랫폼마다 달라진다 | `SP-2` 스파이크. 폴백은 loopback TCP이며 `A-7`로 플러그인화 |
| `A-O-2` | **사용자 목표 머신에 Docker가 없을 수 있다** | `C6`이 v1에서 불가할 수 있다 | `SP-1` 스파이크가 양쪽 경로를 모두 평가. 불가하면 **정적 분석 전용**으로 축소 — 좁지만 거짓말쟁이가 아닌 제품 |
| `A-O-3` | **스펙이 JSON Schema를 배포하지 않는다** | 검증기가 조용히 뒤처진다 | `A-3`의 차분 하네스가 드리프트를 빨간 빌드로 바꾼다 |
| `A-O-4` | **유니코드 `name`의 스펙 불일치** | 한국어 스킬 수용 여부 | 참조 구현을 따르고 `spec_ambiguity`로 노출. 조용히 선택 금지 |
| `A-O-5` | **클라이언트 확장 진화 속도** | 레지스트리가 뒤처진다 | 레지스트리에 `verified_against` 버전 기록. 갱신은 데이터 변경만으로 |
| `A-O-6` | **`C1`의 800 LOC 예산** | Rust에 로직이 새면 아키텍처 붕괴 | CI 검사. 설계가 아니라 **실행 가능 문턱**으로 둔다 |
| `A-O-7` | 어댑터의 지표 미보고 가능 | `timing.json` 불완전 | `AdapterCapabilities`로 선언. `None`으로 기록 (0 금지) |
