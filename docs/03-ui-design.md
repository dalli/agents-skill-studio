## 1. 개요

### 1.1 제품 성격

이것은 **데스크톱 개발자 도구**다. 코드 편집기(Visual Studio Code, Zed,
JetBrains)와 같은 계층의 제품이며, 소비자 앱이나 SaaS 관리 콘솔이 아니다.
[AC-6.1](./04-development-plan.md)이 요구하는 것처럼 스킬의 전체 수명주기를
**터미널 없이** 완결해야 하므로, 모든 판단이 화면 안에서 끝나야 한다.

### 1.2 디자인 원칙 7가지

| # | 원칙 | 내용 | 실패하면 |
|---|---|---|---|
| **P1** | **진단 우선** | 오류를 숨기지 않는다. 경고도 보인다. "0개 진단"이 무엇을 뜻하는지 항상 명시한다 | 스킬이 조용히 깨진다 |
| **P2** | **근본 원인 우선** | "무엇이 잘못되었는지"와 "왜 그렇게 판정했는지"를 함께 제시한다 | 사용자가 고칠 수 없다 |
| **P3** | **정직한 상태** | "아직 없음"·"표시할 수 없음"·"계산 중"·"분석 실패"를 **모두 다른 상태**로 렌더한다 | 조용한 빈 화면은 정확하지 않다 |
| **P4** | **파괴적 작업 확인** | 설치·임포트·덮어쓰기는 항상 계획을 먼저 보여준 뒤 승인받는다 | 되돌릴 수 없는 실수 |
| **P5** | **이식성 경고 전면 노출** | 특정 클라이언트 전용 스킬이면 사용자가 알아야 한다. 경고 burying 금지 | 스펙 통과 → 다른 클라이언트에서 무시됨 |
| **P6** | **키보드 우선** | 전 기능이 키보드로 도달 가능하다. 마우스는 보조 | 느려진다 |
| **P7** | **단일 창** | 컨텍스트 전환을 만들지 않는다. 창을 나누지 않는다 | 흐름이 끊긴다 |

**P3가 이 제품의 특수한 부분이다.** 이 도구가 다루는 대상은
**"있어야 하는 것과 없어야 하는 것의 구분이 어려운 데이터"**다.
진단 0개, 평가 결과 없음, 분석 결과 없음, 설치된 스킬 없음 — 이 네 상태는
모두 화면이 비어 보이지만 의미가 완전히 다르다. 이들을 같은 빈 화면으로
처리하면 사용자는 스킬이 정상이 아니라고 오해하거나, 반대로 문제가 있다고
착각한다.

### 1.3 비범위

| 항목 | 제외 이유 |
|---|---|
| 모바일 레이아웃 | 데스크톱 앱 전용 |
| 실시간 협업 편집 | 단일 사용자 도구 |
| 다크/라이트 외 테마 | 두 테마를 정확히 구현한다. 테마 수를 늘리면 대비 검증 비용이 선형으로 증가한다 |
| 애니메이션 장식 | 성능 · 접근성. 상태 전이에 필요한 최소한만 |

## 2. 정보 구조 (IA)

### 2.1 전체 탐색 모델

```
┌──────────────┬─────────────────────────────────┬──────────────────┐
│              │                                 │                  │
│  사이드바     │        중앙 작업 영역             │  우측 컨텍스트     │
│  240px       │        가변(최소 480px)          │  320px           │
│  (접기 가능)  │                                 │  (접기 가능)      │
│              │                                 │                  │
│  S1 라이브러리 │  S2 편집기 (가장 넓게)          │  O5 Diff 뷰어     │
│  S7 설치관리  │  또는 S4/S5 테스트                │  (컨텍스트에 따라   │
│  S8 임포트    │                                 │   고정/해제)       │
│  S9 설정      │                                 │                  │
│              │                                 │                  │
├──────────────┴─────────────────────────────────┴──────────────────┤
│  상태 바  32px   ● 검증 0 오류 3 경고 │ 프로필: strict │ ~/.agents   │
└────────────────────────────────────────────────────────────────────┘
```

| 영역 | 역할 | 왜 이 위치인가 |
|---|---|---|
| 사이드바 (좌) | **어디로** 이동 | 스킬 선택과 앱 탐색은 빈도가 높고 문맥 독립적이다 |
| 중앙 | **무엇을** 작업 | 폭이 넓을수록 유리하다. 에디터는 가로 폭이 곧 가독성이다 |
| 우측 | **무엇을**olded 검토 | 편집과 대조가 동시에 필요한 작업(검증 리포트, Diff)만 연다 |
| 상태 바 (하) | **지금 어떤 상태인가** | 항상 보이는 사실. 창을 가로지르는 유일한 정보 |

**편집기 폭이 최대여야 하는 이유.** 이 제품의 핵심 작업은
`SKILL.md`를 읽고 고치는 것이다. 라인 래핑이 잦아지면 코드 예시와
YAML 구조가 끊어져 판단을 방해한다. 중앙 영역의 최소 폭을 480px로 두는 이유다.

### 2.3 스킬 하위 화면의 구조 — 탭

**결정: `S3`–`S6`은 탭 구조다.**

```
┌────────────────────────────────────────────────────────────────┐
│ ◀ csv-analyzer                                    ● 검증됨     │
│  ┌──────────┬──────────┬──────────┬──────────┐                │
│  │ 편집     │ 검증  ③  │ 테스트   │ 패키징   │                │
│  │    S2    │    S3    │    S4    │    S6    │                │
│  └──────────┴──────────┴──────────┴──────────┘                │
├────────────────────────────────────────────────────────────────┤
│                     (선택된 탭의 중앙 영역)                      │
└────────────────────────────────────────────────────────────────┘
```

| 대안 | 왜 선택하지 않았는가 |
|---|---|
| **사이드 스텁** | 수직 공간을 steal한다. 에디터에 필요한 높이를 빼앗는다 |
| **별도 라우트 + 전체 레이아웃 교체** | 사이드바·상태 바가 사라져 문맥을 잃는다. `S7`(설치 관리)로 갔다 오는 비용이 크다 |
| **한 화면에 전부** | 이미 복잡하다. 평가 실행 중 검증 리포트까지 같은 화면에 넣으면 밀도가 읽을 수 없다 |

**탭에 배지(badge)를 단다.** `S3`에는 오류 수, `S4`에는 케이스 수를
표시한다. "검사 안 했다"와 "0개다"를 탭 배지만으로 구별 가능해야 한다(§6.3).

```
                    ┌──────────┐

                         ▼                       │

              │  │   └ S5 리포트    │            │
              │  └ S6 패키징 ───────┼──▶ C11     │
              └─────────┬───────────┘            │
                         │                        │
        ┌────────────────┼────────────────┐       │
        ▼                ▼                ▼       │

   │ 임포트 │      │ 뷰어     │     │ 설정   │    │
```

| 전이 | 트리거 | 되돌리기 |
|---|---|---|
| `S1` → `S2` | 스킬 항목 더블클릭 / Enter | 사이드바 |
| `S2` → `S3`/`S4`/`S6` | 탭 클릭 | 탭 |
| `S4` → `S5` | 실행 완료 후 "리포트 보기" | `S4` |
| `S6` → `C11` | "설치" | `S6` |
| `S8` → `O1` | "파일 선택" | `S8` |
| `O1` → `O3` | 파이프라인 3단계 통과 | `O1` |

사이드바의 `S8` 직접 진입이 둘이다. 첫 실행 사용자는 빈 상태의 유도 버튼을,
숙련 사용자는 사이드바를 쓴다.

## 3. 레이아웃 시스템

### 3.1 스플릿 규칙

| 스플릿 | 기본 | 최소 | 최대 | 접힘 |
|---|---|---|---|---|
| 사이드바 ↔ 중앙 | 240px | 0 (접힘) | 420px | `Cmd+B` |
| 중앙 ↔ 우측 | 우측 닫힘 | 260px | 560px | `Cmd+J` |
| `S2` 편집기 ↔ 하단 | 70% | 50% | 85% | 드래그 |
| `S5` 리포트 ↔ 하단 | 65% | 45% | 80% | 드래그 |

**우측 패널이 기본 닫힘인 이유.** `S2`에서 우측 패널이 열려 있는 경우는
Diff를 보고 있을 때뿐이다. 검증 리포트(`S3`)는 우측이 아니라 **중앙 전체**를
사용한다 — 진단 목록은 목록이지 부가 정보가 아니다.

### 3.2 최소 창 크기

| 창 폭 | 레이아웃 |
|---|---|
| ≥ 1440px | 3분할 정상. 우측 패널 동시 표시 가능 |
| 1120–1440px | 우측 패널을 오버레이로 전환 |
| 880–1120px | 사이드바 자동 접힘 |
| < 880px | **지원 최소치.** 최소 880px를 강제하고 좁으면 안내한다 |

**880px를 선택한 이유.** 3분할의 최소 합(사이드바 0 + 중앙 480 + 우측 260)
= 740px이며 여기에 상태 바 여백과 창 테두리를 더하면 880px가 된다.
이보다 좁으면 **편집기가 480px 아래로 내려가** YAML 구조를 읽기 어려워진다.
좁은 화면에서 예뻐 보이는 것보다, **기능을 명시적으로 제한하는 것**이 낫다.

### 3.3 패널 상태 지속

| 패널 | 지속 방식 | 이유 |
|---|---|---|
| 사이드바 폭·접힘 | `localStorage` | 개인 워크플로 |
| 우측 열림/닫힘 | 세션 상태만 | 맥락 의존. 다음 작업에서 그대로 열려 있으면 방해 |
| 하단 분할 비율 | 세션 상태만 | 같은 이유로 리셋이 자연스러움 |
| `S5` 선택된 iteration | URL | 공유 가능해야 함 |

**우측과 하단은 의도적으로 리셋한다.** 접혀 있던 패널이 다음 작업에서
자꾸 열려 있으면 흐름을 방해한다. 사이드바만 지속한다.

## 4. 디자인 토큰

**토큰 하드코딩 금지.** 컴포넌트는 토큰만 참조한다. 색을 직접 쓰면
다크 테마 전환이 깨진다.

### 4.1 색상 — 기준 토큰 8개

| 토큰 | 다크 | 라이트 | 용도 |
|---|---|---|---|
| `--bg-canvas` | `#16181d` | `#ffffff` | 앱 배경 |
| `--bg-surface` | `#1e2128` | `#f7f8fa` | 패널, 카드 |
| `--bg-raised` | `#262a33` | `#ffffff` | 호버, 입력 필드 |
| `--fg-primary` | `#e6e8ec` | `#1a1d23` | 본문 텍스트 |
| `--fg-secondary` | `#9aa3b2` | `#5a6472` | 보조 텍스트 |
| `--fg-muted` | `#6b7480` | `#8a929e` | 비활성, 힌트 |
| `--border-default` | `#333842` | `#dde1e7` | 경계선 |
| `--border-strong` | `#4a515e` | `#c2c8d2` | 포커스 링, 활성 경계 |

### 4.2 상태 색상

**이 5가지 상태는 절대 겹치지 않는다.** `unverifiable`이 `pass`/`fail`의
어느 쪽과도 같은 색이 아니라는 점이 특히 중요하다.

| 상태 | 토큰 | 다크 | 라이트 | 아이콘 |
|---|---|---|---|---|
| `error` | `--state-error` | `#f2777a` | `#c4342f` | `⨯` |
| `warn` | `--state-warn` | `#e5c07b` | `#9a6700` | `△` |
| `info` | `--state-info` | `#61afef` | `#0b6bcb` | `ⓘ` |
| `pass` | `--state-pass` | `#7fd18a` | `#1a7f37` | `✓` |
| `fail` | `--state-fail` | `#f2777a` | `#c4342f` | `✗` |
| **`unverifiable`** | **`--state-unverified`** | **`#8a929e`** | **`#6b7480`** | **`?`** |

`pass`와 `fail`의 색이 `--state-error`와 겹치는 것(라이트 모드)은
의도적이다 — `fail`은 "검증 실패"이므로 error와 같은 의미다. 그러나
**`unverifiable`은 `fg-muted` 계열의 중립 회색**이며 어떤 상태 색과도
겹치지 않는다. 회색은 "판정 결과가 없다"를 뜻한다.

**색만으로 구분하지 않는다(접근성).** 위 표의 아이콘 열을 **항상** 함께
표시한다. 적녹 구분(color-only)은 색각 이상 사용자에게 정보를 지운다.
`error`(빨강·✗)와 `pass`(초록·✓)는 hue와 glyph가 **둘 다** 다르다.

### 5.2 `SkillEditor` — CodeMirror 6 통합

이 컴포넌트가 이 제품의 중심이며, 4가지 통합 문제를 해결해야 한다.

#### 5.2.1 단일 문서, 두 언어

`SKILL.md`는 YAML 프런트매터 + Markdown 본문이다. 두 개를 별도 탭으로
나누면 **사용자가 구조를 볼 수 없다.** 경계를 가상의 문서로 보여 준다.

```typescript
const plugin = keymap.of([
  // --- 구분자 위에서 Enter를 누르면 뒤쪽을 통째로 코드블록이 아닌
  // 프런트매터 편집 모드로 전환하고, 닫는 --- 이후는 Markdown 모드로 전환
  toggleFrontmatterMode,
]);
```

| 구간 | 모드 | 하이라이트 |
|---|---|---|
| `---` ~ `---` | `yaml` | 키·값·중첩 |
| `---` 이후 | `markdown` | 헤딩·리스트·코드펜스 |

**구분자 줄 자체**는 세 가지 상태로 구분한다.

| 상태 | 표시 | 의미 |
|---|---|---|
| 여는 구분자 | `───` (약한 선) | 정상 |
| 닫는 구분자 | `───` + 접힌 배지 | 정상 |
| 닫는 구분자 없음 | `───` + `⨯ 파스 오류` 배지 | `parse_unterminated` |

파스 오류를 **구조 자체에** 표시한다. 사용자가 아래로 스크롤해서
"어디가 문제인지"를 찾아야 한다면 그건 진단이 아니라 탐색이다.

#### 5.2.2 진단 → CM6 decoration 매핑

[02. 데이터 설계 §3.6.1](./02-data-design.md#361-좌표계-규약--wire에서-utf-16-내부에서-코드포인트)이
**유일한 좌표계 규약**이다. 이 절은 그것을 CM6에 적용하는 방법만 다룬다.

**`C12`가 받는 `Span`은 이미 UTF-16 기준이다.**

| 층 | 좌표계 | 누가 변환 |
|---|---|---|
| `C2` 내부 | 코드포인트 | — |
| **wire → `C12`** | **UTF-16** | **`C9` 어댑터** |
| CM6 `pos` / `ch` | UTF-16 (JS 문자열 인덱스) | **변환 없음** |

**따라서 `C12`는 좌표를 변환하지 않는다.** `Span`의 값을 CM6에 그대로 넘긴다.

```
[C2] 코드포인트 offset 42
   │  C9 어댑터가 직렬화 시점에 변환
   ▼
[C12] Span.start.offset = 60  (UTF-16)
   │  변환 없음
   ▼
[CM6] dispatch({ pos: 60 })  → 정확한 문자
```

**왜 이 순서가 강제되는가.** `C12`가 변환하면 두 가지가 깨진다.

| 깨지는 것 | 설명 |
|---|---|
| 규칙의 단일 진실 공급원 | 좌표 변환 규칙이 파이썬과 TS에 **각각** 생긴다. 한쪽을 고치면 다른 쪽이 틀린다 |
| 진단 위치 | TS 변환이 틀리면 **한글이 있는 줄 이후의 모든 진단이 밀린다.** 마커 개수 테스트는 통과한다 |

**`Span.start.line`은 두 계층에서 동일하다 (0-based).** 변환 대상이 아니다.

**A-UI-1 (수정)** — `C2`는 `Span`에 line·column·offset을 **모두 채워
보내되, wire의 값은 반드시 UTF-16 기준**이다. 내부 코드포인트 값이
`C12`에 노출되면 안 된다. `C9`의 변환 테스트
(`test_c9_span_offset_is_utf16`)가 이 불변을 강제한다.

**`span`이 `None`인 진단의 처리.** 파싱 실패처럼 위치를 모르면 gutter
마커를 파일 첫 줄에 놓지 **않는다** — 틀린 위치 표시가 진단보다 해롭다.
대신 [§7.1](#71-진단--에디터-왕복)의 DiagnosticsPanel에 **위치 없음** 그룹으로
모아 **클릭 시 파일 상단**으로 이동시킨다.

#### 5.2.3 프런트매터 인라인 위젯

필드 옆에 간이 위젯을 붙인다. 이 편집은 **구조적**이므로 편집기가 아니라
위젯이 안전하다.

| 필드 | 위젯 | 자동 저장 |
|---|---|---|
| `name` | 텍스트 입력 + 실시간 검증 표시 | Enter/Blur 시 |
| `description` | 다중 행 + **문자 카운터 + 예산 바** | 디바운스 400ms |
| `license` | 텍스트 + 자유 입력 제안 | Blur 시 |
| `compatibility` | 텍스트 + 500자 카운터 | 디바운스 400ms |
| `metadata` | 키-값 편집 테이블 | 즉시 |
| `allowed-tools` | 태그 입력 | 즉시 |
| `description` 하단 | **항상 표시** 힌트: "이 설명은 모든 미래 세션의 시작에 주입됩니다" | — |

**예산 바의 두 눈금.** 1024(스펙 하드)와 1536(클라이언트 트렁크)을
**동시에** 표시한다. [02. 데이터 설계 §4.5](./02-data-design.md#45-설명-예산-2중화)의
이중 예산이므로 하나만 표시하면 사용자가 어느 제한에 걸렸는지 모른다.

#### 5.2.4 파일 탐색기 동기화

`<FileTree>`와 에디터는 양방향으로 동기화된다.

| 이벤트 | 동작 |
|---|---|
| 탐색기에서 파일 선택 | 에디터에 로드, 이전 미저장 상태 확인 |
| 에디터에서 파일 삭제 | 탐색기에서 제거 |
| 외부에서 파일 변경 | 프롬프트 "바깥에서 변경되었습니다" → `O5` Diff로 비교 |
| `SKILL.md` 누락 | `S2`에 치명 오류 배너 + 파일 생성 유도 |

**외부 변경 충돌 처리의 결정.** "자동 재로드"와 "무시"를 기본 offer로
하고, **덮어쓰기는 명시적 선택**이어야 한다. 사용자가 에디터 밖에서 고친
내용을 자동 재로드가 날릴 수 있다.

#### 6.1.1 빈 상태 — 4가지 구별

`S1`의 빈 화면은 **4가지 서로 다른 상태**를 가진다(P3). 하나로 합치면
사용자가 무엇을 해야 하는지 모른다.

| 상황 | 제목 | 본문 | 액션 |
|---|---|---|---|
| 스킬 0개 | "아직 스킬이 없습니다" | "새 스킬을 작성하거나 기존 스킬을 가져오세요." | [+ 새 스킬] [가져오기] |
| **검증 안 함** | "0개의 스킬" | "설치된 스킬이 없습니다." | [가져오기] |
| **오류로 로드 실패** | "2개의 스킬을 읽지 못했습니다" | 각 항목에 원인. "0개입니다"와 **다르다** | [오류 보기] [가져오기] |
| 필터 결과 없음 | "조건에 맞는 스킬이 없습니다" | "필터를 해제하세요." | [필터 해제] |

**"0개입니다"와 "0개의 오류입니다"는 다른 문장이다.** 첫째는 사실이고
둘째는 판정 결과다. 혼동하면 사용자는 스킬이 정상이라고 오해한다.

```
│             │ 스킬 본문…                            │ [수정]   │
│             │                                      │          │
├─────────────┴──────────────────────────────────────┴──────────┤
│ strict ⇄ lenient │ 0⨯ 2△ │ ~/.agents/skills/csv-analyzer       │
└────────────────────────────────────────────────────────────────┘
```

| 항목 | 내용 |
|---|---|
| **목적** | 스킬 작성의 주 작업면 |
| **레이아웃** | 좌 파일 트리 200px · 중앙 에디터 · 우 검증 요약 320px(축소 가능) |
| **데이터** | `SkillDocument`, `Diagnostic[]`, `CapabilityReport` 요약 |
| **액션** | 편집 · 저장(자동) · 검증(자동) · 파일 추가/이름변경/삭제 |
| **우측 패널** | 검증 요약. 클릭 → `S3` 전체 화면으로 |

**우측 패널이 `S3`를 대체하지 않는 이유.** `S3`는 52개 진단을 다룰 수 있는
전용 화면이다. `S2`의 우측은 "지금 이 파일이 어떤 상태인가"의 **빠른
읽기**다. 진단이 5개를 넘어가면 "전체 보기" 링크를 강하게 노출한다.

**부재 상태.** `SKILL.md`가 없으면 편집기 대신 생성 유도 배너를 표시한다.
빈 에디터와 "파일이 없는" 것은 다르다.

### 6.3 `S3` 검증 리포트

```
┌────────────────────────────────────────────────────────────────┐
│ 검증 리포트      [strict │ lenient]  [나란히 보기]   [+ 일괄 수정]│
├────────────────────────────────────────────────────────────────┤
│ [⨯ 오류 0] [△ 경고 2] [ⓘ 정보 1]   [코드 필터 ▾] [경로 필터 ▾]  │

│ ▼ name_dir_mismatch                                          1 │

│   (스펙: name은 부모 디렉터리명과 일치)        [디렉터리 변경] │
│                                                                  │
│ ▼ client_extension_field   2                            [일괄]  │
│   ⨯ SKILL.md:2  context      Claude Code가 존중하나 이식성 위험 │
```

| 항목 | 내용 |
|---|---|
| **목적** | 전체 진단 관리, 일괄 수정, 프로필 대조 |
| **레이아웃** | 중앙 전체 폭. 상단 필터, 중단 그룹 목록, 하단 요약 |
| **데이터** | `Diagnostic[]`, `ValidationProfile`, 차분 준수 결과 |
| **그룹화 기준** | **진단 코드별.** 동일 코드는 같은 수정이 가능하므로 묶는 것이 유용 |
| **액션** | 심각도/코드 필터 · 행 클릭 → `S2` 점프 · quickfix · 일괄 수정 |

**"나란히 보기"의 기능.** `strict`와 `lenient` 결과를 **두 열로** 표시한다.
같은 위반이 `error`와 `warn`로 바뀌는 것을 눈으로 확인한다. 프로필의
차이가 이해되지 않으면 스위치가 무의미해진다.

**차분 준수 결과의 표시.** `C3`가 `skills-ref`와 대조한 결과를 하단에
항상 표시한다. 스펙 드리프트를 사용자가 인지할 수 있는 유일한 지점이다.

```

│ 케이스 (3)              │ 케이스 1 · top-months-chart          │

│ ○ 2 결측 이메일 정리    │ 프롬프트                             │
│ ○ 3 빈 파일             │ ┌──────────────────────────────────┐ │
│                         │ │ data/sales_2025.csv에서 상위 3개… │ │
│ [필터]                  │ └──────────────────────────────────┘ │
│                         │                                      │
│                         │ 기대 출력                             │
│                         │ ┌──────────────────────────────────┐ │

│                         │       ☐ old_skill (스냅샷: 없음)     │

│                         │ 모델: claude-sonnet-4-5              │
│                         │                                      │

│                         │                                      │
├─────────────────────────┴──────────────────────────────────────┤
│ ⏱ with_skill  ████████████░░░░  3/6  루트:~$0.20   [취소]     │
├────────────────────────────────────────────────────────────────┤
│ ▸ 로그  │ ⓘ iteration-1 기준 2회 반복 권장 (stddev 산출 필요)  │

```

| 항목 | 내용 |
|---|---|
| **목적** | eval 케이스 정의와 실행 제어 |
| **레이아웃** | 좌 케이스 목록 240px · 우 케이스 편집 + 실행 패널 |
| **데이터** | `EvalSuite`, `EvalCase`, `RunRequest`, `StreamEvent` |
| **진행 표시** | 하단 진행 바. arm별, 케이스별 진행 + 누적 비용 |

**`old_skill`를 조건부로 노출하는 이유.** 스냅샷이 없으면 비활성이다.
"이전 버전 기준선"은 **스킬을 수정하기 전에 스냅샷을 떠야** 존재한다.
그래서 편집 화면에 "기준선 스냅샷 만들기"를 노출한다(AC-2.11).

**비용·시간 예측을 실행 전에 표시하는 이유.** LLM 실행은 돈과 시간이 든다.
예측 없이 "▶ 실행"만 두면 사용자는 함부로 누른다. 이전 반복 기록이 있으면
평균에서 예측하고, 없으면 "첫 실행 — 소요 시간 미예측"을 명시한다.

```

├────────────────────────────────────────────────────────────────┤
│ 채점 요약                                                       │
│  with_skill      3/9 통과 (33%)      without_skill   1/9 (11%) │
│  ────────────────────────────  ▲ +22%p                           │
│  시간  45.2s ±12.0              32.1s ±8.4         +13.1s       │
│  토큰  3,800 ±400               2,100 ±300         +1,700      │

│ ▼ 케이스 1 · 상위 3개월 차트                     with │ without  │

│                                                                  │

│   ★ 스킬의 실제 가치 (2)                                      │

│     • 차트 이미지 파일을 포함한다                             │
│     • 정확히 3개월이 표시된다                                  │
│   ⚠ 스킬 없이도 통과 (1)  — assertion이 스킬의 가치를 재지…   │
│   ✗ 양쪽 모두 실패 (1)      — assertion 또는 케이스를 점검…   │
│   ⓘ 편차 큼 (0)                                              │
├────────────────────────────────────────────────────────────────┤
│ 사람 검토 (feedback.json)                                        │
│   케이스 1: 축 라벨이 없고 월이 알파벳순으로 정렬되어 있다.       │
│   케이스 2:                                                        │
├────────────────────────────────────────────────────────────────┤

```

| 항목 | 내용 |
|---|---|
| **목적** | 채점 결과 해석, 개선 방향 파악 |
| **레이아웃** | 중앙 전체. 요약 → 채점표 → 패턴 분석 → 사람 검토 순서 |
| **데이터** | `Grading`, `Benchmark`, `AssertionAnalysis`, `Feedback` |

**요약 → 채점표 순서인 이유.** 사용자는 먼저 "좋아졌나?"를 보고 그다음
"왜?"를 본다. 반대 순서는 원인을 찾기 전에 숫자에 압도된다.

**`?` (unverifiable) 행이 반드시 눈에 띄어야 한다.** `evidence`가
"판정 근거가 출력을 인용하지 않아 검증 불가로 기록됨"이라는 **설명 행**을
가진다. 조용히 `fail`로 세면 사용자는 스킬을 고칠 대상이 아닌 판정기를
고치게 된다.

**반복 1회일 때의 강제 표시.** benchmark 행 아래에
`ⓘ 반복 1회 — 표준편차는 2회 이상 반복 시에만 표시됩니다`를 **항상** 노출한다
(AC-2.7). 표준편차 영역에 `—`를 넣되, 이것이 의도된 제한이 아니라
**데이터가 부족한 상태**임을 함께 말한다.

**feedback 빈 줄의 의미.** 케이스 2의 빈 입력란은 "아직 검토 안 함"이
**아니다.** `""`는 "검토했고 이상 없음"이다. `Feedback`의 이 구분을
그대로 UI에 반영한다([02. 데이터 설계 §7.6](./02-data-design.md#76-feedback--사람의-검토)).
따라서 입력란 옆에 상태 배지를 둔다: `검토됨 · 이상 없음` 또는 `미검토`.

|---|---|

**고정 파라미터를 편집 가능하게 하지 않는 이유.** 이 값들을 바꾸면
**재현성이 깨진다.** AC-3.1은 "같은 입력 → 바이트 동일"을 요구한다.
따라서 이 표는 **정보 제공**이며 설제가 아니다.

**`manifest.json`이 아카이브 외부인 이유를 UI에도 말한다.** 아카이브를
풀지 않고 신원을 확인할 수 있다. 해시 불일치로 아카이브가 손상되었을 때
진위를 판단할 근거가 필요하다.

```
┌────────────────────────────────────────────────────────────────┐

│ csv-analyzer      스튜디오          설치됨      ✓ 보임          │
```

| 항목 | 내용 |
|---|---|
| **목적** | 설치 상태와 **실제 가시성** 관리 |
| **데이터** | `VisibilityReport`, `InstallTargetView`, `SkillProperties` |
| **핵심 열** | **가시성** — "설치됨"과 "로드됨"은 다른 열 |

**가시성 열을 독립시킨 이유.** [01. 아키텍처 §8.3](./01-architecture.md#83-설치-성공이-거짓말이-되는-4가지-경우)의
4가지 함정을 사용자에게 드러내는 유일한 지점이다. `broken-skill`은
**설치에 성공했고 로드에도 성공하지만 실행 시 실패한다** — "설치됨" 열만
보면 문제가 전혀 보이지 않는다.

**예약 이름이 `✗ 보이지 않음`인 이유.** 조용히 로드되지 않기 때문이다.
"이름을 바꾸면 됩니다" 액션을 함께 제시한다.

| **레이아웃** | 중앙 640px 고정. 다이얼로그가 아니라 **화면** |
| **데이터** | 경로 안전성 판정, `Diagnostic[]`, `CapabilityReport` |

**`S8`이 화면인 이유.** 파이프라인은 6단계이고 각 단계가 별도 확인을
요구할 수 있다. 다이얼로그 안에 넣으면 단계 진행과 상세 판정을 동시에
볼 수 없다.

**경로 안전성 실패는 "취소"와 "다른 소스"만 offer한다.** 이 우회 경로는
없다. 통과·실패 선택지가 있는 확인 다이얼로그와 **구별**되어야 한다.

| 상태 | 표현 | 스위치 |
|---|---|---|
| 사용 가능 | `● 사용 가능 (Docker 29.8.1 감지)` | 활성 |
| 미설치 | `⚠ 컨테이너 런타임 없음 — 정적 분석만 사용됩니다` | **비활성** |
| `SP-1` 미통과 플랫폼 | `⚠ 이 플랫폼에서 격리를 검증하지 못했습니다` | **비활성** |

**스위치를 비활성으로 두는 이유.** 켜져 있는데 실행되지 않는 상태는
가장 혼란을 부른다. 실패-닫힘(`A-2`)은 UI에서도 동일하게 적용된다 —
"켜져 있지만 안 된다"를 "켜져 있다"고 표시하면 안 된다.

**`reports_tokens=false` 어댑터를 기본값으로 삼을 때의 경고.** `timing.json`의
토큰이 비게 되므로 `benchmark`의 비용 항목을 채울 수 없다. `S9`에서
경고를 표시하고, `S5` 리포트에서 `—`로 보이는 것이 그 결과다.
사용자가 비용을 인지 못하면 반복 실행이 예상치 못하게 청구된다
([03. §7.5.2](./03-ui-design.md#752-benchmark-시각화와-저수량-상태)의
저수량 상태와 같은 취지).

**자격증명 취급 원칙.** `S9`는 **키 값을 절대 표시하지 않는다.** OS 키체인에
있고, 화면에는 존재 여부와 마지막 4자리만 보인다. 스킬이나 프로젝트 파일에
credential을 쓰는 경로는 없다 — 스킬은 사용자 프로젝트에 배포되므로
평문 키가 리포지에 커밋될 수 있다.

### 7.1 진단 → 에디터 왕복

```
[사용자가 DiagnosticRow 클릭]
   │
   ▼
[C12] span 있음?
   ├─ 예 → cm.dispatch({ effects: setSelection(pos) })
   │        + scrollIntoView + 포커스
   │        + 선택 영역 강조 (1.5초간 --state-info 배경)

```

**빠른 수정의 실행과 되돌리기.**

| quickfix 종류 | 적용 방식 | Undo |
|---|---|---|
| `replace_span` | CM6 `dispatch` → `changes` 트랜잭션 | ✅ 편집기로 되돌림 |
| `insert_field` | CM6 `dispatch` | ✅ |
| `move_to_metadata` | **구조 편집**. 별도 트랜잭션 + 확인 | ✅ (단, 구조가 바뀌므로 설명 필요) |
| `none` | 메뉴에서 수동 안내만 | — |

**A-UI-2** — 모든 quickfix는 **Undo 가능**해야 한다. 되돌릴 수 없는
자동 수정은 "진단 우선"의 반대다. 사용자가 수정을 검증했다가 원복할 수
없으면 다음부터는 quickfix를 쓰지 않는다.

**span 좌표가 어긋난 경우의 자기 보호.** 파싱 성공 후 재계산된 오프셋이
파일 길이를 넘으면(예: 외부 편집으로 문서가 축소됨) decoration을 적용하지
**않고** DiagnosticsPanel에 "진단 위치를 재계산하는 중"을 표시한다.
틀린 위치에 밑줄을 그리는 것은 진단보다 해롭다.

### 7.2 검증 프로필 전환

**결정: 결과는 즉시 재계산하되, 규칙 엔진은 하나다.**

`strict` ⇄ `lenient` 전환 시:

| 동작 | 구현 |
|---|---|
| 규칙 재실행 | **하지 않는다.** 같은 결과를 다시 쓰고 심각도만 바꾼다 |
| 소요 시간 | <16ms (심각도 맵 조회) |
| UI 갱신 | 즉시 |

**"재계산하지 않는다"가 올바른 이유.** `C3`가 두 프로필을 **하나의 규칙
엔진 + 심각도 맵**으로 구현했으므로([02. 데이터 설계 §3.7](./02-data-design.md#37-프로필--하나의-규칙-엔진-하나의-심각도-맵)),
프로필 전환은 데이터 변환이다.

> ⚠ **이 변환을 클라이언트가 하면 규칙 엔진이 둘이 된다 (설계 결함).
> [01. 아키텍처 §2.1](./01-architecture.md#21-단일-진실-공급원-single-source-of-truth)은
> `C12`의 **규칙 재구현을 금지**한다. 클라이언트가 심각도 맵을 들고 있으면
> 그것이 두 번째 규칙 엔진이고, 맵이 바뀌면 두 곳을 고쳐야 한다.
>
> **해결: `C3`가 두 프로필의 결과를 **한 번에** 함께 보낸다.**

**해결책 — 한 응답에 두 결과를 실어 보낸다.**

```python
class ValidatedSkill(BaseModel):
    """한 번의 검증 호출이 **두 프로필**의 결과를 함께 돌려준다."""

    strict: list[Diagnostic]     # severity = strict 기준
    lenient: list[Diagnostic]    # severity = lenient 기준
    codes: list[DiagnosticCode]  # 두 결과에 공통인 코드 집합
```

`DiagnosticCode`는 프로필과 무관하므로 두 결과의 **코드 집합은 동일**하다.
차이는 오직 `severity` 필드다. 그러므로:

- `C3`는 규칙을 **한 번** 실행하고 심각도만 두 벌로 채운다.
- wire에 **`D-TEST-6`이 강제한다**: 두 리스트의 `code` 시퀀스가 같아야 한다.
  다르면 규칙 엔진이 둘로 갈라졌다는 뜻이다.
- `C12`는 **심각도 필드만 갈아끼워** 렌더한다. 규칙 판단을 하지 않는다.

이렇게 하면 프로필 전환은 왕복 0회로 즉시 일어나면서도
**규칙의 단일 진실 공급자가 유지된다.**

**"나란히 보기" 모드.** 두 결과를 두 열로 표시한다. 각 행에
`error → warn` 전이가 화살표로 보인다. 프로필 차이를 **이해하게** 하는 것이
목적이며, 같은 행이 두 열에 나란히 있어야 비교가 된다.

### 7.3 정적 분석 결과 표시

`CapabilityReport`의 배치. **위험 신호와 정보 신호를 같은 비중으로 두지 않는다.**

**상태 A — 실행 표면이 있는 경우.**

```
┌────────────────────────────────────────────────────────────────┐
│ 실행 표면 분석                                    [재분석]     │
├────────────────────────────────────────────────────────────────┤
│ ⛔ 위험 3                                                        │
```

**상태 B — 실행 표면이 있는 것 중 위험이 없는 경우.**
`findings`가 **비어 있지 않지만** `dangerous` 등급이 없을 때. 정보 섹션만
나온다. `findings == []`인 진짜 무발견 상태와 **구분**한다.


**상태 B′ — `findings == []`일 때 (진짜 실행 표면 없음).**
정보 섹션조차 없다. "아무것도 발견되지 않았다"와 "발견할 게 없었다"의
차이를 사용자가 알 수 있게 한다.

```
┌────────────────────────────────────────────────────────────────┐
│ 실행 표면 분석                                    [재분석]     │
├────────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────────────────────────────────────┐   │
│ │ ✓ 실행 표면 없음                                          │   │
│ │ 이 스킬은 SKILL.md 본문에서 명령을 실행하지 않고,          │   │
│ │ 등록된 훅이나 사전 승인된 도구도 없습니다.                  │   │
│ └──────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────┘
```

**상태 C — 분석 자체가 실패한 경우.** "발견 사항 없음"과 **반드시 구분한다.**

```
┌────────────────────────────────────────────────────────────────┐
│ 실행 표면 분석                                    [재분석]     │
├────────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────────────────────────────────────┐   │
│ │ ⚠ 분석하지 못했습니다                                     │   │

│ │ [권한 확인] [다른 경로 선택]                               │   │
│ └──────────────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────────────┘
```

> ⚠ **상태는 동시에 표시할 수 없다 (앞 판본의 결함).**
> "위험 3"과 "✓ 실행 표면 없음"이 같은 화면에 나온 것은 **논리적으로
> 불가능**하다. 앞 판본은 또 다른 결함도 있었다 — "`findings == []`일 때
> 상태 B"라고 규칙을 써놓고는 **정보 섹션을 렌더한 예시**를 보여줬다.
> 규칙과 예시가 어긋나면 구현자는 예시를 따라간다. 그래서 아래 표가
> 유일한 규칙이다.

**배치 규칙 (`C12` 구현 요구 — 이 표가 유일한 진실).**

| `analysis_complete` | `findings` | 렌더 |
|---|---|---|
| `false` | 무관 | **상태 C만.** 위험/정보 섹션을 그리지 않는다 |
| `true` | `dangerous` 있음 | **상태 A.** 위험은 **최상단**, 그 아래 정보 |
| `true` | `info`만 있음 (비어 있지 않음) | **상태 B.** 위험 섹션 생략, 정보만 |
| `true` | `[]` | **상태 B′.** 정보 섹션도 없음 |

| 요구 | 구현 |
|---|---|
| 위험은 **최상단** | `severity=dangerous`는 목록 위, 별도 섹션 |
| 본문 실행은 개별 강조 | `body_shell_exec`는 스킬 본문이 실행될 수 있다는 의미이므로 **항목 숨김 금지** |
| 실행 표면 없음 = 긍정 신호 | 상태 B. 초록 테두리 박스 |
| 정보는 하단·중립 색 | `--state-info`, 위험 색을 쓰지 않는다 |
| **분석 실패 ≠ 안전** | 상태 C. `E13`은 차단 사유가 된다 |
| 실제 코드 조각 표시 | `evidence` 필드를 그대로 렌더 |

**`evidence`를 보여주는 이유.** "본문 셸 실행이 있습니다"보다
`` !`curl …` `` 가 함께 있어야 사용자가 **위치와 내용을** 판단한다.
FINDING의 `evidence`가 이 역할이다.

**위험을 축약하지 않는 규칙.** 위험 항목에 "펼치기"를 두지 않는다.
3줄 요약으로 항상 보인다. 축약은 항목 수를 은닉하므로 이 제품의 원칙
`P1`에 어긋난다.

### 7.4 L3 평가 실행

```
[실행 클릭]
   │
   ├─ 1. 사전 검증: 스킬 상태, 어댑터 준비, 케이스 유효성
   │      └─ 실패 시 실행하지 않고 사유 표시
   │
   ├─ 2. 비용/시간 예측 표시 (이전 반복 평균 기반)
   │
   ├─ 3. O4 실행 확인 (실행 횟수 > 4회 또는 arm > 1개면)
   │
   ├─ 4. StreamEvent 수신 시작
   │      ├─ run_started     → 진행 바 등장
   │      ├─ case_started    → 케이스별 상태
   │      ├─ stdout/stderr   → arm별 콘솔에 append
   │      ├─ case_completed  → 채점 표시
   │      └─ benchmark_ready → "리포트 보기" 활성화
   │
   └─ 5. 실패 시: [O4 취소] 또는 [이 케이스만 재시도]
```

**`O4` 실행 확인이 필요한 조건.** 실행이 돈을 들이므로 다음 중 하나면
확인한다: 총 실행 횟수 > 4, arm 2개 이상, 실 제공자(`MockAdapter` 제외).

**`MockAdapter`는 확인 없이 실행.** 비용이 0이고 CI용이므로.

**스트리밍 로그의 tabs 구조.**

| arm | 탭 | 내용 |
|---|---|---|
| `with_skill` | `with_skill` | 실행 로그, 도구 호출, 파일 생성 |
| `without_skill` | `without_skill` | 동일 |
| `old_skill` | `old_skill` | 동일 (활성화 시) |

**긴 줄 처리.** 줄바꿈을 기본으로 하되, JSON·diff처럼 구조가 있는
출력은 가로 스크롤을 허용한다. 모든 줄을 강제로 접으면 `eval` 트레이스
구조를 읽을 수 없다.

**취소 시 부분 산출물 보존.** 취소는 **run 전체를 버리지 않는다.** 이미
생성된 `outputs/`와 `timing.json`은 남기고 상태를 `run_cancelled`로 기록한다.
왜 끊었는지 나중에 다시 봐야 하는 경우가 있다.

**`disable-model-invocation` 스킬의 특별 취급.** with_skill arm 로그
상단에 노란 배지:

```
ⓘ disable-model-invocation: true — 자동 활성화를 건너뛰고 명시적으로 로드했습니다.
   실제 Claude Code에서는 이 스킬이 자동 활성화되지 않습니다.
```

이 배지 없으면 사용자는 "스킬이 안 먹혔지"를 추적할 수 없다 (AC-2.1e).

### 7.5 평가 리포트

#### 7.5.1 3상태 시각적 구분

| verdict | 아이콘 | 색 | 라벨 |
|---|---|---|---|
| `pass` | `✓` | `--state-pass` | 통과 |
| `fail` | `✗` | `--state-fail` | 실패 |
| `unverifiable` | `?` | `--state-unverified` | 판정 불가 |

**`unverifiable`이 중립 회색이어야 하는 이유.** 이 상태는 "스킬이 나쁘다"도
"스킬이 좋다"도 아니다. **판정 시스템이 스스로를 신뢰하지 못한 상태**다.
`fail`의 빨강으로 칠하면 스킬을 고치라는 잘못된 신호가 되고,
`pass`의 초록으로 칠하면 검증이 통과한 것처럼 보인다. 중립 회색만이 정직하다.

**`?` 행 아래의 설명은 필수다.**

```
? 양 축에 라벨이 있다
  판정 근거가 실제 출력을 인용하지 않아 검증 불가로 기록됨
```

사용자가 "판정 불가"의 원인을 알고 자기 assertion을 다듬을 수 있어야 한다.

#### 7.5.2 benchmark 시각화와 저수량 상태

```
시간    45.2s ±12.0        32.1s ±8.4        +13.1s
        ├─────┤             ├────┤            ▲
        ▓▓▓▓▓▓▓▓▓▓▓         ▓▓▓▓▓▓▓▓          느리지만 개선폭 대비 합당
```

**반복 1회일 때의 강제 규칙.** 표준편차 영역을 **차트에 그리지 않고** —
**텍스트로 대체한다.**

```
시간    45.2s               32.1s             +13.1s
        (표준편차 없음)        (표준편차 없음)
ⓘ 반복 1회 — 표준편차는 2회 이상 반복 시에만 표시됩니다
```

**차트에 `0`이나 빈 공간으로 그리는 것을 금지한다.** 사용자는
"편차가 0으로 측정됐다"고 읽을 수 있다. `stddev=None`은 **데이터 부재**이지
**편차 0**이 아니다. 이 구분이 AC-2.7의 핵심이다.

**3회 이상이면 에러 바를 표시**하고, 분포(min/max 뱃지)를 추가한다.

#### 7.5.3 4종 패턴 분석 카드

`AssertionAnalysis`를 우선순위 순으로 정렬해 카드로 표시한다.

| 우선순위 | 패턴 | 강조 | 메시지 |
|---|---|---|---|
| 1 | `only_with_skill` | **초록** | "스킬의 실제 가치" |
| 2 | `fails_both` | 빨강 | "양쪽 모두 실패" — assertion이나 케이스 점검 |
| 3 | `passes_both` | 노랑 | "스킬 없이도 통과" — 통과율을 부풀림 |
| 4 | `high_variance` | 파랑 | "편차 큼" — 지시 모호 또는 flaky |

`only_with_skill`만 **카드 상단에 고정 배치**한다. 사용자가 스킬을
유지할 근거이며, 다른 세 패턴은 개선 대상이다. 이 비대칭이 도구의
목적을 드러낸다.

### 7.6 임포트 신뢰 게이트 (`O3`)

```
┌────────────────────────────────────────────────────────────────┐
│ 이 스킬을 설치하시겠습니까?                                     │
│ source-registry/csv-analyzer                                   │
├────────────────────────────────────────────────────────────────┤
│ 스펙 검증                                    ⨯ 오류 1         │
│   ⨯ name_dir_mismatch   디렉터리 이름이 스킬 이름과 다릅니다     │
│   → [자동 수정]  디렉터리 이름을 'csv-analyzer'로 변경           │
│                                                                  │
│ 실행 표면                                      ⛔ 위험 2       │
│   ⛔ 본문 셸 실행   !`curl …` 가 로드 시 실행됩니다               │
│   ⛔ 도구 사전 승인 allowed-tools: Bash(curl:*) Read             │
│                                                                  │
│ ⚠ 지속적 영향                                                     │
│   이 스킬의 description(128자)은 이후 이 컴퓨터의 모든 세션 시작  │
│   에 주입됩니다. 이 텍스트를 바꾸려면 SKILL.md를 편집해야 합니다.  │
│   description은 1024자 이내, Claude Code 목록 한도 1536자 이내.  │
│                                                                  │
│ [취소]                                          [차단 사유 무시] │
│                                              └ name 오류는 무시 불가│
└────────────────────────────────────────────────────────────────┘
```

**P4(파괴적 작업 확인)의 구현.** 기본값은 **취소**다. 승인 버튼이 시각적으로
크지 않고, 취소가 기본 포커스다.

**경로 안전성 실패는 이 게이트에 오지 않는다.** 앞에서 이미 거부된다.
이 게이트에서 다루는 위험은 "설치해도 되는가"이며, "해석이 불가능한
입력"이 아니다.

**무시 가능한 것과 없는 것을 구분한다.** 이 구분이 없으면 사용자는
"O3는 왜 이름을 못 고치는데 위험은 무시할 수 있지?"라고 느낀다.

| 항목 | 무시 가능 | 이유 |
|---|---|---|
| `name_dir_mismatch` | ❌ | 자동 수정 가능. 무시할 이유가 없음 |
| `client_extension_field` | ⭕ | 이식성 문제일 뿐 위험 아님 |
| `body_shell_exec` | ⭕ (명시적 동의) | 사용자가 이해하고 결정 |
| 경로 안전성 위반 | ❌ | 해석 불가 |
| 분석 실패(`analysis_complete=false`) | ❌ | **분석 실패는 안전이 아님** |

**설치 거부 항목이 드러나는 배치.** 무시 불가 항목이 있으면 승인 버튼의
레이블이 "위험 무시하고 설치"가 아니라 **비활성**이 되고, 사유가 버튼
아래에 직접 적힌다.

### 7.7 설치 및 가시성

```
[설치 계획 확인]
┌────────────────────────────────────────────────────────────────┐
│ 설치 계획                                                       │
│ 대상    ~/.agents/skills/csv-analyzer/  (사용자 · 크로스 클라이언트)│
│ 동작    새로 설치                                                 │
├────────────────────────────────────────────────────────────────┤
│ ⚠ 경고 1                                                        │
│   project-scope에 같은 이름의 스킬이 있습니다.                    │
│   이 컴퓨터에서는 project가 우선합니다 (우선순위 규칙).           │
│   설치 후 project 스킬이 이 스킬을 가립니다.                      │
│   [project 스킬 보기]                                            │
├────────────────────────────────────────────────────────────────┤
│ [취소]                                                [설치]    │
└────────────────────────────────────────────────────────────────┘
```

**설치 후 결과 — 반드시 두 경우를 구분한다.**

```
✓ 설치 완료 — csv-analyzer
  ~/.agents/skills/csv-analyzer/
  클라이언트가 이 스킬을 찾습니다.                        [S7 보기]

✓ 설치 완료 — old-skill
  ~/.agents/skills/old-skill/
  ⛔ 이 이름은 Claude Code에서 예약되어 있어 로드되지 않습니다.
     [이름 바꾸기 →]                                   [S7 보기]
```

**두 번째 경우가 이 설계의 목적이다.** "설치 성공"을 `✓`로만 표시하면
사용자는 문제가 있다고 알 수 없다. 설치 성공과 **로드 가능성**은
별개의 사실이다.

**모노레포 검증 위치.** 프로젝트 스킬의 가시성 검증은 **사용자 세션이
실제로 시작될 위치**를 기준으로 수행한다. 저장소 루트가 아니라
`packages/frontend/`에서 시작한 세션은 그 경로와 모든 부모를 탐색한다.
검증 위치가 다르다(AC-3.6).

`Cmd/Ctrl+K` 또는 `Cmd/Ctrl+P`. **화면 전환과 자주 쓰는 액션**만 노출한다.

|---|---|---|
| **탐색** | 스킬 라이브러리로 이동 | — |

| | 검증 리포트 | 스킬 이름 (입력) |
| | 테스트 러너 | 스킬 이름 (입력) |
| | 설치 관리 | — |
| | 임포트 | 소스 (입력) |
| **액션** | 새 스킬 만들기 | 스킬 이름 (입력) |
| | 검증 실행 | — |
| | 평가 실행 | — |
| | 실행 취소 | — |
| | 기준선 스냅샷 만들기 | — |
| **설정** | 프로필 전환 | strict / lenient (선택) |

**명령 팔레트에 노출하지 않는 것.** 파괴적 명령("스킬 삭제")은
포커스가 오간 사이 실수될 수 있으므로 제외한다. "설치"는 파라미터가
두 개(스킬, 대상)여서 흐름이 복잡하므로 제외했다. 모두 `Cmd+K`를 열지
않으면 실행된다.

## 10. 상태 · 데이터 흐름

### 10.1 상태 소유권

| 상태 | 위치 | 근거 |
|---|---|---|
| 검증 결과 | **서버**(`C3`). 클라이언트 캐시 | 규칙은 파이썬에 있다. 프런트가 재구현 금지 |
| capability report | **서버**(`C5`) | 동일 |
| `Grading`/`Benchmark` | **서버**(`C7`) | 계산은 코어 |
| 프로필(현재 선택) | **클라이언트** | UI 상태. 서버에 영속 불필요 |
| 선택된 iteration | **URL** | 공유 가능해야 함 |
| 에디터 버퍼 | **클라이언트** | 디바운스 후 서버로 전송 |
| 파일 트리 | **클라이언트** | `C4`가 목록을 제공하되 펼침 상태는 UI 소유 |
| 샌드박스 활성화 여부 | **설정**(영속) | P4: 명시적 사용자 결정 |
| 어댑터 자격증명 | **OS 키체인** | 스킬이나 프로젝트 파일에 두지 않는다 |

**"검증 결과는 서버 권위"가 규칙 단일성과 직결된다.** `C12`가
진단 결과를 로컬에서 만들면 `C3`와 두 규칙이 생긴다. 클라이언트는
`spec.validate`를 호출해 결과를 **표시**할 뿐, 판정하지 않는다.

### 10.2 스트리밍 데이터 전달

`StreamEvent`는 `stdio`를 통해 `C1`이 `C12`로 전달한다
([01. 아키텍처 §3.3](./01-architecture.md#33-전송-계층)).

| 처리 | 구현 |
|---|---|
| 순서 | `seq` 단조 증가. 클라이언트가 **갭 감지** |
| 백프레셔 | `C12`가 최근 500개 버퍼. 스크롤이 위일 때만 리플로우 |
| 지연 표시 | 300ms 이상 이벤트 없으면 "기다리는 중" 표시. **행이 계속되면 표시 안 함** |
| 유실 | `seq` 갭 감지 시 "일부 로그가 누락되었습니다" 배너 |
| 대용량 | 청크 단위 append. 전체를 메모리에 모으지 않음 |

**행이 계속되면 "기다리는 중"을 표시하지 않는 이유.** LLM 호출은 5초 이상
걸리는데 로그가 안 나오는 시간이 정상이다. 매번 표시하면 사용자는
"멈췄나"를 오판하고 취소한다.

### 10.3 파일 변경 감지

```
[파일시스템 이벤트]           [정기 스캔]
       │                            │
       ▼                            ▼
  C4: 파일 변경 알림            C4: 상대 경로 해시 비교
       │                            │
       └────────┬───────────────────┘
                ▼
        캐시 스탬프 불일치? ── 예 ──▶ C3 재검증 → C12 갱신
                │ 아니오
                ▼
          이벤트만 신뢰
```

**A-UI-3** — 파일시스템 이벤트는 **최적화이며 유일한 근거가 아니다.**
이벤트를 놓칠 수 있으므로, `C12`는 화면 복귀 시와 저장 시점에 **상대 경로
해시를 비교**해 캐시 유효성을 확인한다. 이벤트만 믿으면 오래된 검증
결과가 표시된다([01. 아키텍처 `A-14`](./01-architecture.md#92-캐시)).

**충돌 시 UX.** 이미 버퍼에 편집 내용이 있을 때 외부 변경이 발생하면
**`O5` Diff 뷰어**로 세 선택지를 제시한다.

| 선택 | 동작 |
|---|---|
| 내 변경 유지 | 외부 변경을 **버린다**. 경고 배너 표시 |
| 외부 변경 채택 | 버퍼를 교체. **현재 편집 내용은 `localStorage`에 임시 보관** |
| 수동 병합 | Diff 뷰어에서 편집 |

**"외부 변경 채택"이 편집 내용을 버린다는 사실을 명시**한다. 조용히
바꿔서 편집을 잃는 것은 가장 나쁜 결과다.

### 10.4 긴 작업 상태

| 작업 | 표시 위치 | 취소 |
|---|---|---|
| 평가 실행 | `S4` 하단 진행 바 | `O4` 취소. 부분 산출 보존 |
| 카탈로그 스캔(5000+) | 상태 바 진행 | — |
| 아티팩트 빌드 | `S6` 버튼 스피너 | — |
| 샌드박스 실행 | `S2` 콘솔 | 강제 종료 |

**취소 불가 작업을 명시한다.** 아티팩트 빌드는 중간에 취소하면
반쪽 상태가 남을 수 있으므로 취소 버튼을 두지 않는다. 스캔은 읽기
전용이므로 취소가 불필요하다.

### 10.5 캐시와 재계산

| 데이터 | 캐시 키 | 무효화 조건 |
|---|---|---|
| 카탈로그 | — | 파일시스템 이벤트 **또는** 스탬프 불일치 |
| 검증 결과 | `(relpath, content_hash, profile)` | `content_hash` 변경 |
| capability report | `(relpath, tree_hash)` | 트리 해시 변경 |
| benchmark 평균(예측용) | `(skill, iteration)` | 새 반복 완료 |
| 파일 트리 | `root` | 이벤트 **또는** 주기 스캔 |

**검증 캐시의 키에 `content_hash`와 `profile`가 모두 들어가는 이유.**
파일 내용은 프로필과 무관하고 프로필은 내용과 무관하다. **둘 다** 키에
포함해야 캐시 오염이 없다. 하나만 넣으면 프로필 전환 후 결과가 섞인다.

## 11. 접근성

### 11.1 키보드 전 기능 접근

| 영역 | 접근 방법 |
|---|---|
| 사이드바 | `Tab` 순회, `Cmd+1..4` |
| 파일 트리 | `Tab` + 방향키. 접기/펼치기는 `Space`/`→` |
| 에디터 | `Tab` 삽입, `Esc`로 트리 복귀 |
| 진단 목록 | `Tab` + 방향키, `Enter`로 에디터 점프 |
| 오버레이 | 열리면 포커스 **가두기**. `Esc`로 닫고 **원래 위치로 복귀** |
| 명령 팔레트 | 위/아래 선택, `Enter` 확정, `Esc` 취소 |
| 진행 바 | 취소 버튼은 `Tab` 도달 가능 |

**포커스 복귀는 반드시 구현한다.** `O3`를 닫으면 **닫기 전 요소로**
포커스가 돌아간다. 그렇지 않으면 사용자는 탐색을 처음부터 반복한다.

### 11.2 색 외 병용

| 정보 | 색 외 대체 |
|---|---|
| 심각도 | 아이콘(`⨯ △ ⓘ ✓ ✗ ?`) + 텍스트 라벨 |
| diff 추가/제거 | `+` / `−` 머리 기호 |
| 선택된 arm | 좌측 3px 막대 + 굵은 글꼴 |
| 섀도잉 상태 | 텍스트 라벨. 아이콘 병기 |
| 활성 탭 | 2px 하단 밑줄 + 굵은 글꼴 |

`error`·`pass`는 hue와 glyph가 다르므로 **색각 이상 시에도** 구별된다.

### 11.3 스크린리더 라이브 리전

| 대상 | `aria-live` | 빈도 제한 |
|---|---|---|
| 검증 결과 개수 | `polite` | 검증 완료 시 |
| 평가 진행 | `polite` | 케이스 완료 시. **stdout 청크는 아님** |
| 실행 실패 | `assertive` | 오류 발생 시 |
| 설치 완료 | `assertive` | 완료 시 |
| 스트리밍 로그 | `off` | 읽지 않는다. **사용자가 직접 탐색** |

**스트리밍 로그를 라이브 리전에 넣지 않는 이유.** 토큰마다 읽으면
화면 리더가 실행을 따라갈 수 없다. 로그는 `log` 역할의 정적 영역이고,
진행 요약만 별도 라이브 리전으로 알린다.

### 11.4 모션과 대비

| 항목 | 처리 |
|---|---|
| `prefers-reduced-motion` | 모든 전환·애니메이션을 `0ms`로 |
| 강제 색상 모드 | `forced-colors` 대응. 상태 표시가 색이므로 **아이콘이 필수**가 된다 |
| 확대 200% | 레이아웃이 수직으로 스택되도록. 가로 스크롤 발생 가능하나acceptable |
| 최소 창 880px 미만 | 안내 후 기능 제한 |

## 12. 오류 · 엣지 상태 카탈로그

일반화되지 않은 오류를 전부 표로. `S2` 기준 우선순위.

| # | 상황 | 표시 | 사용자 액션 |
|---|---|---|---|
| E1 | 백엔드 연결 끊김 | 중앙 배너 "코어가 응답하지 않습니다 (재시도 중)" + 재시도 버튼 | 재시도 / 로그 열기 |
| E2 | 계약 버전 불일치 | **전체 화면 차단 다이얼로그**. 양쪽 버전 + 해결 방법 | 업그레이드 안내. 재시도 불가 |
| E3 | `SKILL.md` 없음 | `S2` 치명 배너 + "생성" 버튼 | 생성 |
| E4 | **검증 대상 없음** | "검증할 파일이 없습니다" — 0개 진단과 **구별** | `SKILL.md` 생성 |
| E5 | 파일 외부에서 삭제 | `S2` 배너 "이 파일이 삭제되었습니다" | 되돌리기 / 다른 파일 |
| E6 | 파싱 실패(span 없음) | **위치 없음** 그룹으로 이동. gutter 마커를 **않 그린다** | 파일 상단에서 직접 확인 |
| E7 | 평가 런 실패 | 해당 케이스만 `실패` 표시, 다른 케이스 계속 | 재시도 / 로그 보기 |
| E8 | 어댑터가 토큰 미보고 | `benchmark` 토큰 칸에 `—` + "이 어댑터는 토큰을 보고하지 않습니다" | 어댑터 변경 |
| E9 | **샌드박스 가용 불가** | `S9` 스위치 비활성 + 사유. 실행 시도 시 오류 | 정적 분석만 사용. **폴백 없음** |
| E10 | 임포트 소스 도달 불가 | `S8` ① 단계에 오류. git 인증 실패 구분 | 재시도 / 다른 소스 |
| E11 | 설치 대상 쓰기 불가 | `InstallPlan` 단계에서 차단. 권한 안내 | 권한 변경 / 다른 대상 |
| E12 | 디스크 공간 부족 | 오류 + 필요 공간과 사용 가능 공간 | 정리 후 재시도 |
| E13 | **분석 실패** | `CapabilityReport`에 "분석하지 못했습니다". **안전으로 표시 금지** | 파일 권한 확인 / 재분석 |
| E14 | 반복 1회 | benchmark에 `ⓘ 반복 1회 — 표준편차 산출 불가` | 반복 늘려 재실행 |
| E15 | 어댑터 없음 | `S4` 실행 버튼 비활성 + "어댑터를 설정하세요" | `S9`로 이동 |
| E16 | `old_skill` 스냅샷 없음 | arm 체크박스 비활성 + "스냅샷이 없습니다" | 스냅샷 만들기 |
| E17 | 외부 변경 충돌 | `O5` Diff + 3선택지 (§10.3) | 선택 |
| E18 | 경로 안전성 위반 | `S8` ② 단계에서 **취소/다른 소스만** offer | 다른 소스 |

**E4와 E1의 구별이 특히 중요하다.** "진단 0개"(성공)와 "검증 대상 없음"
(실행 안 됨)은 화면이 **비어 있어도** 완전히 다르다. E4는 전용 배너를
갖는다. 조용한 빈 화면은 사용자가 "정상"으로 오해하게 만든다(P3).

**E9의 표현이 실패-닫힘의 UI 대용이다.** 샌드박스가 불가한 상태에서
스위치가 켜져 보이면 사용자는 "왜 안 되지"를 이해할 수 없다. 스위치가
**비활성이고 사유가 보인다**면 상태가 정확하다.

**E13의 표현이 신뢰 게이트의 전제다.** 분석 실패를 "발견 사항 없음"으로
표시하면 안전 게이트가 통과되어 **위험한 스킬이 설치**된다. 분석 실패는
그 자체로 **차단 사유**가 된다.

## 13. 검증

각 화면의 관찰 가능한 진술. `lsp_diagnostics`는 타입 검사로 **기능
증명이 아니므로** 런타임 관찰이 필요하다.

### 13.1 자동 검증 (Playwright 가능)

| 시나리오 | 관찰 가능한 진술 | 방법 |
|---|---|---|
| V1 | 최소 유효 스킬을 열면 진단 0개 | `error` 카운터 `0` |
| V2 | 이름 불일치 스킬을 열면 gutter에 정확히 1개 마커 | 마커 개수 `1` |
| V3 | **한국어 이름 스킬에서 진단 0개** | `name_charset` 부재 |
| V4 | `strict`→`lenient` 전환 시 코드 **동일**, 심각도만 변경 | 코드 집합 동일, 심각도 이분 |
| V5 | 진단 클릭 시 에디터 커서가 해당 span | `selection` 위치 == span |
| V6 | quickfix 적용 후 Undo로 원복 | 버퍼 원문 일치 |
| V7 | `scripts/` 없는 스킬의 본문 `!`cmd`` 탐지 | `body_shell_exec` 1건 |
| V8 | `KEY=!`cmd`` 는 미탐지 | 탐지 0건 |
| V9 | 실행 1회 반복의 `stddev`가 `None` | "표준편차 없음" 텍스트 |
| V10 | evidence 없는 판정이 `unverifiable` | verdict `?` |
| V11 | 경로 안전성 위반 시 승인 버튼 부재 | 버튼 0개 |
| V12 | 예약 이름 설치 시 "로드되지 않습니다" 배너 | 텍스트 존재 |
| V13 | `SKILL.md` 부재 시 E4 배너 | 배너 텍스트 |
| V14 | 프로필 전환이 서버 왕복 없이 즉시 | 네트워크 0건 |

### 13.2 수동 검증 (Playwright로 어려움)

| 시나리오 | 이유 | 관찰 |
|---|---|---|
| M1 | **CodeMirror 진단 언더라인 위치** | 한글 문자가 있는 파일에서 언더라인이 **정확한 문자** 위에 있는지 눈으로 확인. UTF-16 오프셋 오류는 이에서만 드러난다 |
| M2 | Tauri 창 최소 크기 880px 레이아웃 | 창을 좁혀 스택 확인 |
| M3 | OS 키체인 자격증명 흐름 | 시스템 프롬프트 동작 |
| M4 | 다크/라이트 대비 | 두 테마 모두 §4.7 기준 충족 |
| M5 | `prefers-reduced-motion` | 모션 제거 확인 |
| M6 | **긴 평가 실행의 스트리밍 유실** | 장시간 실행 중 `seq` 갭 배너 동작 |
| M7 | 외부 편집 충돌 UX | 터미널에서 파일을 편집하고 `S2`로 복귀 |
| M8 | 포커스 복귀 | `O3` 열고 닫은 뒤 포커스가 원 위치인지 |

**M1이 이 문서에서 가장 중요한 수동 검증이다.** V2는 "마커가 1개"만
확인하지만, M1은 "**어느 문자 위에** 있는가"를 확인한다. UTF-16 코드유닛
불일치 버그는 마커 개수 테스트를 통과하면서 **위치가 한 칸씩 밀려** 통과한다
([02. 데이터 설계 §3.6](./02-data-design.md#36-span-quickfix-diagnostic)).
**한글 파일로만 드러나는 버그이며, 자동 테스트로는 잡히지 않는다.**

### 13.3 시각 회귀

| 대상 | 기준 | 허용 |
|---|---|---|
| 9개 화면 | 주요 테마 2개 라이트/다크 | 스냅샷 비교 |
| 상태 6종 | 배지 렌더 | 0.1% 픽셀 |
| 레이아웃 3분할 | 창 폭 3단(1440/1200/900) | 0.1% 픽셀 |

**픽셀 차이 허용치를 0으로 두지 않는 이유.** 폰트 힌팅과
GPU 레더링은 플랫폼마다 미세하게 다르다. 0% 차이를 요구하면 CI가
노이즈로 실패하고, 팀은 비교를 끈다. **구조적 차이가 있으면 반드시
잡히고, 안티에일리어싱 차이만 허용**하는 수준이 실용적이다.
